# 引擎适配调研报告（E 草案 · 2026-08-02 夜班远征）

> H44 调研先行的产物：三引擎无头自动化能力盘点 + agent 可驱动性评级 + 适配层设计建议。
> 结论供《游戏开发管线总协议》（同目录草案）引用；升级路径：制作人批准后并入 C/B 级。

## 一、结论速览

| 维度 | Godot 4.7 | Unity 6 | Unreal 5.7+ |
|---|---|---|---|
| 无头执行 | ✅ `--headless` 原生，全流程零 GUI | ✅ `-batchmode -nographics`；**2026-07 新增独立 `unity` CLI**（`unity test`、NUnit XML、标准退出码、终端内 eval C#） | ✅ UAT/commandlet 体系（`RunUAT.bat BuildCookRun`），CI 成熟但笨重 |
| 工程文件形态 | **全明文**（project.godot/.tscn/.gd 手写即可）——与透明化宪法天然同宗 | 半明文（YAML 场景/prefab + 二进制库缓存；meta 敏感） | 二进制为主（.uasset/.umap），**agent 直接手写不可行**，只能经代码/commandlet |
| agent 直写工程 | ✅ 本机实测：手写文本工程 → headless import → 无头测试 3/3 → 退出码正确 | ⚠️ 脚本/asmdef 可直写；场景/prefab YAML 可写但易碎；导入靠 batchmode 触发 | ❌ 资产必须经引擎侧工具生成；C++/蓝图混合，蓝图不可文本编辑 |
| 测试自动化 | `--script` SceneTree 脚本（本机已验证）；生态有 GUT/GdUnit4 | Test Framework：`-runTests -testResults xml`；新 CLI `unity test` 更顺 | Automation Framework + `-RunAutomationTests`（Functional Test 蓝图/C++） |
| 构建产物 | `--export-release`（需导出模板 ~1GB；已知怪癖：无 .godot 缓存时需先 `--import`，#95287/#69511） | `-buildTarget` + build 脚本 executeMethod（方法须 static 无参） | `BuildCookRun -cook -pak -package` |
| 本机状态 | ✅ 4.7.1 便携版已装 `D:\engines\godot\`（84MB）| ✅ 6000.3.10f1 已装（⚠ TK 工程 6000.1.9 版本不匹配——batchmode 打开会静默升级工程，**禁止直接对 TK 跑**）；新 `unity` CLI 未装（单独分发） | ❌ 未装（30-100GB 级，按需再装） |
| agent 可驱动性评级 | **A**（最佳拍档） | **B+**（成熟但仪式多、慢启动） | **C**（可自动化，但资产黑箱+体量大，适合"程序职能"单线介入） |

## 二、关键事实与坑（各引擎）

### Godot
- 冒烟三件套（本机验证）：`--headless --path . --import` → `--headless --script res://test_xxx.gd`（SceneTree 脚本 assert+quit(code)）→ `--export-release <preset>`（preset 在 export_presets.cfg，明文）。
- 导出已知怪癖：headless 导出前必须确保 import 缓存存在；`--editor --quit` 强制重导入的老偏方在新版不可靠（#69511），管线里显式跑 `--import` 一步。
- 生态：auto-godot（专为 agent 工作流的第三方 CLI，直改文本工程不开编辑器）值得跟踪。
- 2D 尤其强：tilemap/精灵管线全文本可组装——2D 项目首选引擎适配。

### Unity
- 2026-07-20 官方发布独立 `unity` CLI + 实验性 com.unity.pipeline 包：`unity test` 跑 EditMode/PlayMode 输出 NUnit XML（测试失败退出码 6）、可向运行中的编辑器 eval C#。**这是 agent 集成的正确未来**，但需单独安装（本机未装，列入待办）。
- 传统姿势（现有可用）：`-batchmode -nographics -quit -executeMethod 类.静态无参方法` + `-runTests -testResults out.xml`；首次导入冷启动分钟级——管线设计必须容忍慢启动（监工超时按量级放宽，D 级惯例已有）。
- **版本纪律（新坑入案）**：batchmode 打开版本不匹配的工程会静默升级 ProjectSettings——引擎适配层必须先校验 `ProjectVersion.txt` 与本机编辑器一致，不一致直接拒开。
- meta 文件敏感：agent 写区纪律要求"新增资产成对生成 .meta 交给引擎"或"batchmode 触发导入生成"，禁止手编 guid。

### Unreal
- 自动化入口统一走 `Engine/Build/BatchFiles/RunUAT.bat`：BuildCookRun（构建/烘焙/打包）、`-RunAutomationTests`（Automation Framework）。
- 资产（.uasset/.umap）二进制：agent 的施展面收窄为 **C++ 源码 + Python 编辑器脚本（Editor Scripting）+ commandlet**——写区矩阵里美术/装配的"直写资产"模式对 UE 不成立，需改为"脚本生成资产"模式。
- 体量与许可：装机 30-100GB、构建吃 CPU/内存巨大；按项目真实需要再装，不预装。

## 三、适配层设计建议（模块化宪法的引擎版）

仿 artgen 通道注册表/providers 注册表，建 **enginectl 引擎通道注册表**：

```
tools/enginectl/enginectl.js
  通道：godot-test / godot-export / unity-test / unity-build / (unreal-* 预留)
  每通道声明：引擎定位（路径探测）、版本校验、冒烟命令、产物位置、退出码语义
  调用方（装配/QA agent、执行器探针）只认通道名——换引擎不换协议
```

配套协议点（供总协议草案引用）：
1. **项目注册表加 `引擎` 字段**（unity/godot/unreal + 版本）——探针按引擎做全链自检，章程按引擎给写区；
2. **版本校验前置**：引擎通道执行前校验工程版本 = 本机引擎版本，不符拒开（Unity 静默升级坑）；
3. **写区矩阵按引擎特化**：Godot=全文本直写；Unity=脚本直写+资产经导入；UE=仅代码与脚本化生成；
4. **冒烟即验收底线**：每引擎通道自带冒烟命令，装配单的"能进能玩"以通道冒烟出口码为准。

| 验证项 | 结果 | 证据 |

| Unity 版本纪律拒开路径 | ✅（设计验证） | ProjectVersion.txt ≠ 本机版本时返回拒开 JSON，未触碰 TK 工程 |

新入案坑（已吸进工具/写进报告）：
- Unity `-createProject` 生成的工程 **不含 test-framework 包**——manifest.json 需补 `com.unity.test-framework` 才能编译 NUnit 测试（否则批处理报编译错误退出）；
- Godot `--export-release` **不自动创建输出目录**，目录缺失时导出静默失败（exit 1 而 stdout 只见 import 扫描）——enginectl 已改为自动 mkdir；
- Godot 导出模板 tpz ~1GB，解压落位 `%APPDATA%\Godot\export_templates\<版本>.stable\`。
