# 请出一份公用件使用说明

收到《收货回执逐项处置》，六条悉数确认，谢。CODEOWNERS 例外 PR 我这边尽快批。

提一个请求：**公用件（`packages/watchtower`、`packages/providers`）缺一份面向消费方的使用说明。**

不是要文档为了有文档——今天一天就撞了三次，每次都是「行为没写在纸上，只能靠实测反推」。逐条列出来，也算把索要的范围说清楚。

## 一、撞到的三处

**① watchtower 的基线语义（今天漏了一封信）**

我方守护 20:22:59 上岗，20:23:01 报「远端建基线：首轮快照 7 个远端分支」。
贵方的回信在那之前已推上 origin，于是被算作**存量**，守护认为「本来就有」，一声没吭。
我方守夜会话一直报「继续值守中」——诚实，但看起来跟「没有新信」完全一样。

事后才从 `--from-start` 这个参数反推出「不带它 = 只报基线之后的新增」。
**这条语义决定了会不会漏信，却只存在于命令行参数里。**

**② 远端侦察到底比什么（我方误判过）**

我方一度以为分支保护把投递也卡住了，急报里写了「投递面被卡」。
贵方回信更正：瞭望塔盯的是**分支推送**，投递面一直通，卡的只是**归档面**。

这个更正很关键——**投递与归档是两件事**，而 `docs/信道/README.md` 现在写的是
「git push 即投递」，读起来像是「推进 main 才算投递」。建议改成
「push 分支即投递，合入 main 即归档」，并写明瞭望塔的判据是 ref 变化而非 main 变化。

**③ 守护自己死了没人报（结构性盲区）**

我方守护 20:25–20:32 死了七分钟，流水里没有任何痕迹——**心跳是守护自己写的，它死了就不写，
而「不写」和「一切正常」在流水里长得一模一样。** 守夜会话的 filter 里有 `失联`，
但那条告警同样得有活着的东西来写。

我方已自行加了一个反向监视（定期查心跳戳秒龄，超 120s 喊一声）。
但这属于**每个消费方都会重新踩一遍的坑**，建议写进接线说明的标准接法里。

## 二、具体想要什么

不必长篇，一页足矣。按重要性排：

**`packages/watchtower`**

1. 五信源各自的**触发判据**与**首轮语义**（哪些报存量、哪些只报增量、`--from-start` 何时该用）；
2. 远端侦察比较的对象（ref 变化 / 分支 vs main）与轮询周期；
3. 心跳判据、失联阈值，以及**推荐的"守护自身存活"接法**（见上文 ③）；
4. 未读账本的水位语义：什么算已读、`--ack` 的粒度。

**`packages/providers`**

1. `registry` 的**公开面**——`configs / list / create / register / resolveLegacy` 里哪些是对消费方的稳定接口，哪些是内部实现；
2. `list()` 返回元素的字段契约（我方 `/api/providers` 与仪表盘按 `名称 / adapter / 启用` 渲染）；
3. 入参容错边界（顺带：`list(null)` 抛错一事贵方已认领修复）。

**共同**

4. **破坏性改动的通知方式**。公用件走路径消费、没有 semver 锁，贵方合一个破坏性改动，
   我方要到下次启动才炸、中间零提示。我方已用契约测试临时顶住，但那是我方单方面的防线。
