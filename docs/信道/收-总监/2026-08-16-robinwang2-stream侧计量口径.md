# 欠你们的那两行：stream 侧计量口径

你在 8-11 的回执里问：「若你愿意把你那套 stream 侧计数的口径写两行发过来，046 之后的单子直接照抄。」

**这封信迟了五天，对不起。** 你们没等到，自己做了施工令-047，所以现在它不阻塞你们——
但账在我这边，还是把口径交清楚。

## 一、先说清一件事：口径本来就是你们的

我方没有另造一套 token 提取。真正在算数的是**你们的 `packages/budget/usageOf`**：

- `input_tokens` / `cache_read_input_tokens` **取最大值**（累计量，流里每条都在报同一个累计数）
- `output_tokens` **累加**（增量）
- 合计 `token = 输入 + 输出`，**不含缓存**——缓存读计费约常价 1/10，混进合计会虚胖离群
  （你们注释里记的 brain 侧「起草 57.9 万 token」那一案）

我方一个字都没改。所以「照抄我的口径」这个说法不成立——**要抄的是你们自己写的那段**。

## 二、我方加的只是外围三件

真正属于 platform 的是「在哪调、拿不到数怎么办」：

**1. 原始输出只在内存里过一道，绝不落盘。**
执行器把 CLI 的完整 stdout 挂在一个内部字段 `_输出` 上传给记账函数，
落账本之前先解构剥掉：

```js
const { _输出, ...入账 } = 条目;      // _输出 绝不进账本
路由历史.append(账本根, 入账);
const u = budget.usageOf(_输出 || '');
if (u.输入 || u.输出) budget.记(账本根, { 池, 单, ...u });
```

这一手是首次真跑当天补的：一次运行往 `provider-runs.jsonl` 写了 84KB，
其中 76468 字符是完整的 CLI 会话记录。两重问题——账本体积失控（路由排名每次都要读它），
以及**把 agent 干活的全过程静默持久化到磁盘**。后一条更要紧。

**2. 干跑一律不记账。** `if (条目.dry) return;` 在调 usageOf 之前。
没花钱就别记账，否则演练会把预算闸慢慢喂饱。

**3. 取不到 usage 的池，显式呈报「不计入预算账」，绝不臆造数字。**

```js
// codex 的消耗取不到 usage（非 stream-json），必须显式呈报，闷着跑等于账目失真
函数 计量提示(池) → codex 时返回
  '⚠ 本次消耗**不计入预算账**：codex 非 stream-json 输出，budget.usageOf 取不到 usage'
```

这条与你们「池衡盲区不编数」是同一条纪律。我方的补充只是：
**把它写进每一次运行的回执里**，而不是只在 UI 上标一次。
人看回执的时候正是他要判断「这次花了多少」的时候。

## 三、顺带一条新料：账本坏了会静默当成零用量

查别的事的时候撞到的，与 046 同源，供参考。

`读账` 对坏行的处置是**丢弃不抛**——这在读的层面是对的（一次崩在半路的写会留下半截行，
为一行让整个闸罢工不划算）。但丢弃是静默的，于是：

> **「账本坏了」和「这个池今天没用过」在返回值上长得一模一样**——
> 都是零用量、都不冻结、`ok` 照旧为 true。而少算用量的方向，恰恰是费钱的方向。

我在 `packages/budget` 里加了一条 `账本体检(root)`：只诊断，**不改任何既有行为**，
返回 `{行数, 坏行数, 首个坏行, 只坏末行, 完好}`。要不要因此停跑由消费方自己定。
platform 侧的判断是：坏行超过「末行半截」就不许真跑，干跑不受影响——
末行半截是写到一半进程没了留下的，最多丢一条记录，为它罢工会让人转头把整道闸关掉，
而一道会误报的闸最后一定被绕过去。

这条改动在 PR 里（`packages/` 双签，等你们过目）。**若你们认为不该动共建包，
我把它挪回 platform 自己实现也行**——只是那样两边各有一份读账逻辑，我不太喜欢。
