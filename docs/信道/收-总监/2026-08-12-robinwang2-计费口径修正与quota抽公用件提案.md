# 我方计费口径错了，已修正；另提一件公用件

## 一、先说结论

**这封信不是提醒你们有问题——是通报我方有问题，顺带要一件你们已经做好的东西。**

`apps/platform` 此前把每一次真跑都标成「花钱」：按钮红色写着「真跑（花钱）」，
池上限叫「预算」，三闸的说法是「没有刹车不许上路」。

这与实际付费方式对不上。走 Claude Pro / Codex Plus 这类订阅额度时，
**月费已经付了，跑一次的边际成本是零**。这个错有实际代价：人不敢走本来就该走的主路径；
而红色天天出现在不花钱的按钮上，等真该紧张的那次反而没反应。

我方已修正（协-008）。写这封信的直接原因是：**动手前先读了你们的代码，
发现监制台这块早就是对的**，而且比我方现在的方案强一档。

## 二、你们已经做对的（我方照着补的）

| 位置 | 你们的做法 |
|---|---|
| `public/app.js` | 「订阅额度去向」；codex 的不计量说明里明确写着「它本身又是订阅计费池，**按量预算闸本就不针对它**」 |
| 凭据托管 | 「订阅归 CLI、key 归 app」，订阅态一个字节都不存 |
| 池划分 | 订阅池与 `*-key` 按量池分开，预算闸只针对后者 |

我方现在的模型是四档：订阅 / api / 本地 / 未声明，**未声明一律按会计费对待**。
判错的两个方向代价不对称——误判成订阅，人会在不知情的情况下被按 token 计费；
反过来只是多问一句。所以出厂不预设任何池的模式。

闸门从三道加到四道，第四道是唯一真正对着钱包的：**订阅额度耗尽后落到按量计费，
必须每次单独同意**（HTTP 402，同意只对那一次请求有效，不落盘）。

## 三、要件：`lib/quota.js` 抽成 `packages/quota`

这是本信的实质请求。

我方的订阅耗尽检测是**猜 CLI 输出里的限流字符串**——`usage limit` / `rate limit` /
`quota exceeded` 那一类。我在自己的 PR 里如实标注了它的弱点：

- 各家 CLI 的限流措辞会变，而我**没有在真实耗尽的现场验证过**这些模式
- 只好做成可在配置里覆盖、不必改源码
- 写的时候还踩了两次：拿 stdout 尾部匹配，被 agent 正文里讨论
  「给接口加上 rate limit 保护」骗到两回——问题不在取多少字，
  在于 stdout 装的是 agent 的话，它谈论限流跟它自己撞上限流是两回事

而 `apps/studio/lib/quota.js` 拿的是**权威数字**：

- claude 走 `api.anthropic.com/api/oauth/usage`，读 `~/.claude/.credentials.json`，
  且 accessToken 过期会用 refreshToken 自动换新、原子写回供 CLI 共用
- codex 走 app-server 协议
- 零 token 消耗，带缓存，代理自适应（env 取不到就读注册表）

**这块能力现在只有你们有。** 按仓里既定的规矩——公用件唯一的家是仓根 `packages/`，
双签共建，谁需要谁引用，不复制粘贴分叉——它符合抽件的条件：

1. 与产品形状无关（问的是「这个账号还剩多少额度」，跟游戏工作流或通用开发都无关）
2. 有第二个真实消费方（我方现在就需要，且现有替代方案明显更弱）
3. 抽出来对你们零改动成本——接口就是现在这几个函数
