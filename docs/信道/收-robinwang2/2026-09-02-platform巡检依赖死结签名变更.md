# apps/platform 的 `依赖死结()` 签名改了，附带 test 加了 11 行

## 一、改了什么

`apps/platform/lib/巡检.js`

```js
- function 依赖死结(全部工单) {
-   const 表 = new Map((全部工单 || []).map((t) => [String(t.id), t]));
+ // 待判工单可排除有效挂起单，但依赖查表必须保留全集：挂起的上游仍然存在，
+ // 不应被误判为「依赖缺失」。
+ function 依赖死结(待判工单, 全集工单 = 待判工单) {
+   const 表 = new Map((全集工单 || []).map((t) => [String(t.id), t]));
```

第二个参数有默认值，**旧的单参数调用行为不变**。

同批还动了三份文档与一份新文档：
`docs/接线说明.md`、`工程队/协-001-工单库.md`、`docs/存量挂起受害清单.md`（新）。

## 二、为什么

出自 studio 侧的 **TK-192「挂起字段保真与巡检识别」**。挂起这个特性天然跨两个 app：
挂起字段在 studio 定义（`fm.挂起`，不新增状态族），而**认这个字段的巡检住在 platform**。

不改的后果具体是：巡检把有效挂起单排除出待判集时，连带把它从依赖查表里也去掉了；
于是任何以挂起单为上游的单都会被判成「依赖缺失」——**而挂起的上游其实还在**。
`docs/存量挂起受害清单.md` 是当时列的受害单。

## 三、判据

`apps/platform/test/产线契约.test.js` 加了 11 行覆盖这一条。
提交前实跑 studio 全量：**套件 126 · 断言 1498 · 耗时 49.0s · 红 0**。

## 四、这件事是怎么发生的，以及它暴露的问题

这份改动**在工作树里躺了五天**才被提交。时间线：

- 内容出自 TK-192 执行过程，改完没提交
- 2026-08-28 17:47:58 一次 `git checkout`（从 `信道/2026-08-28-回codex沙箱` 切回
  `tk-189-gantt-red-bar`）重写了 37 个文件的 mtime，改动跟着一起留在工作树里
- 2026-09-02 清点工作树时才发现，与 studio 的 46 处改动一起提交

**这不是第一次。** 08-25 有个提交就叫「产线在途快照（共树止血）：多张在途单的工作树改动整…」，
是同一件事的上一轮。

暴露的问题是：**CODEOWNERS 只在 PR 时请求评审，本机直接改文件不受任何约束。**
一张 studio 的单可以正当地需要改 platform，而没有任何东西拦它、也没有任何东西记录它。
按现在的机制，你只会在某次 pull 之后发现自己的 app 变了，且不知道为什么。

这封信是在补那个「记录」。但补一封信不等于把洞堵上——如果你觉得需要一道机器闸
（比如提交时按 CODEOWNERS 路径分组、跨地盘的改动强制单独成一提交并投信道），
可以在回执里提，那需要双方都认。
