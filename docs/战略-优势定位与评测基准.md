# 战略 · 优势定位与评测基准

> 2026-08-08。竞品扫描 + 定位判断 + 一条可执行的 benchmark 路径。
> **这是战略判断，不是从代码里验证出来的事实**——除了第二节那份数据，那个是实的。
> 竞品信息来自当日公开检索，来源列在文末。

---

## 一、竞品扫描结论：有一大群邻居，没有正面撞车的

三类邻居，各占一块：

**① 并行 agent 编排器（最直接）** —— Vibe Kanban、kanban-code、Nimbalyst、Conductor 一类。
形态高度一致：**看板 + git worktree 隔离 + 并行跑 Claude Code / Codex**，
卡片自动关联 session、worktree、tmux、GitHub PR。

与我们重合的是 worktree 隔离与多 agent 并行（即 platform 那套的核心）。
区别在于他们止步于「看板管会话」，没有状态机、判官链、额度闸。

> ⚠️ **平台方已下场**：Claude Code 于 2026-02-05 随 Opus 4.6 发布 Agent Teams，
> 多 session 互相通信、共享任务、自协调。**编排这一层正在被商品化。**

**② Markdown 即事实源（撞得最狠）** —— [Backlog.md](https://github.com/MrLesk/Backlog.md)
几乎是「目录即状态机」（D19）的同款主张：任务是仓库里的 `.md`、YAML frontmatter、
看板就是目录、状态变更即文件改动、git 成为状态机，带验收标准与依赖，还有 MCP server。

社区已把这个模式提炼成话术：「`.md` 不再是文档，是人与 agent 之间的**协议层**」。
**方向被验证了，但不构成壁垒。**

**③ Agent 治理 / 护栏（我们最被低估的部分）** —— 行业共识与我们的设计惊人一致：
编排框架（LangGraph / CrewAI）**只管怎么跑，不管生产策略**——谁能批准写库、
token 预算多少、哪个动作要人闸。而「人闸不是瓶颈，是业务判断真正加值的质量控制点」
这句话，基本是宪法第五条（人本化）的英文版。

背景数字：Gartner 预测 2026 年 agent 软件支出达 2065 亿美元，
同时预计**超过 40% 的 agentic 部署会在生产中失败**。没人能回答为什么、怎么提前知道。

## 二、真正的资产：一份别人结构上拿不到的数据

`lifecycle.验收()` 里已经有这一段：

```js
const 误 = !通过 && 核查章.结论 === '通过' ? '漏判'
         : (通过 && 核查章.结论 === '不过' ? '误杀' : null);
if (误) ledger.score(root, { 线: '审检误判', 席: '核查', 单: id, 类型: 误 });
```

**每当机器判官与人的最终裁决不一致，系统自动记一笔。**
加上 H69 三条评分线（审检评执行 / 执行评拆单 / 项管评审检），
我们在**日常运营的副产品里持续生成一份带标签的判官准确率数据集**。

这个东西别人做不出来，不是技术难，是**结构上不具备**——
他们没有「人对同一份产出做最终裁决」这一步。没有那一步就没有 ground truth，
就永远只能说「我们的 agent 很好」而拿不出数字。

**而整个行业最缺的恰恰是数字。**

## 三、定位：做纪律层，不做编排层

> **给无人值守 agent 生产线用的纪律层。**

不是「又一个能并行跑 Claude Code 的看板」——那条赛道已经拥挤，且平台方已下场。

我们与别家 approval gate 的本质区别：**他们的是外挂的工作流节点，我们的是状态机的结构性属性**。
单子物理上进不了「完成」目录，除非人签了字。这不是配置，是形态。

编排在被商品化，治理还是空的。**往判官链、额度纪律、审批点走，比往看板和 worktree 走安全。**

## 四、benchmark 路径（三步）

### 第一步：把已有埋点变成公开指标

原料都在，缺的是口径定义与发布：

| 指标 | 现有数据源 |
|---|---|
| 判官**漏判率 / 误杀率** | `项管台账/评分.jsonl` 的「审检误判」线 |
| 一次通过率（无自修交付） | 工单 `自修次数` |
| 人闸触发率（多少单真需要人） | 待定夺 / 保留单占比 |
| 单位交付成本 | 预算账（施工令-021）+ 回执实耗 |
| 判官链故障率 | `判官重试上限` 计数、执行失败原因分布 |
| **空壳交付拦截率** | `settleClose` 各条拒绝分支的命中数 |

最后一条尤其值钱——**「如果没有判官链，多少空壳会混过去」**，
这是那些防御代码的量化价值，目前只存在于注释里的事故编号中。

### 第二步：出一个可复现的评测套件

一个标准参考仓库 + 一组标准工单，**含故意埋雷的**：需求含糊的、验收标准不可判定的、
会诱导 agent 越界的。任何编排器都能跑，输出同一组指标。

这一步是关键转折：**从「参赛者」变成「裁判」**。
别人评测自己的编排器时用我们的套件，我们的架构就成了参考实现。

### 第三步：公开事故档案

`settleClose` 的空输出/光板结论/结论无法判读、H63 软超时验尸、活尾巴取样、
死代理判红——每一条背后一个真实事故编号。整理成一份
**《无人值守 agent 的失效模式清单》**。

这是抄不走的可信度，因为它只能被烧出来。别人读完会发现自己踩过其中一半却没记录。

## 五、三个会杀死这个计划的东西

**① 仅 Windows。** 一个 benchmark 如果只能在 Windows 上跑，没人会采用。
**这是硬阻塞，不是优化项。**

**② 样本量。** 22 张单 + 一个游戏项目的量出不了统计意义；
判官误判率要几百张单才有说服力。没有捷径——
好处是**它跟正常干活是同一件事**，不需要额外投入，只需要时间与纪律。

**③ 既当裁判又当选手。** 指标定义若与产品绑死，没人信。
做法是把**指标规范**（一份 spec + 一个参考数据格式）与**实现**分开发布，
让别人能在自己的编排器上产出同格式数据。我们可以是第一个实现，**但不能是唯一可能的实现**。

---

## 六、如果只能做一件事

**先把「判官误判率」这一个指标做实、做久、公开。**

它同时满足四个条件：

1. 数据已经在流（零额外开发即可开始积累）；
2. 别人结构上拿不到；
3. 直接回答行业最痛的问题——**AI 审 AI 到底有没有用**；
4. 天然就是 benchmark：**一个数字，可比较，可复现**。

其余都可以往后排。

顺带一提：「studio 还是 platform」（见 [`工程队/议题-一个整机还是两个产品.md`](../工程队/议题-一个整机还是两个产品.md)）
在这个坐标系里不算要紧事——**两套 profile 共用一条判官链，反而让样本量翻倍**，
这本身就是选 B（一个整机两套 profile）的又一条理由。
