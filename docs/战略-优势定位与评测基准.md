# 战略 · 优势定位与评测基准

> 2026-08-08。竞品扫描 + 定位判断 + 一条可执行的 benchmark 路径。
> **这是战略判断，不是从代码里验证出来的事实**——除了第二节那份数据，那个是实的。
> 竞品信息来自当日公开检索，来源列在文末。

---

## 一、竞品扫描结论：有一大群邻居，没有正面撞车的

三类邻居，各占一块：

**① 并行 agent 编排器（最直接）** —— Vibe Kanban、kanban-code、Nimbalyst、Conductor 一类。
形态高度一致：**看板 + git worktree 隔离 + 并行跑 Claude Code / Codex**，
卡片自动关联 session、worktree、tmux、GitHub PR。

与我们重合的是 worktree 隔离与多 agent 并行（即 platform 那套的核心）。
区别在于他们止步于「看板管会话」，没有状态机、判官链、额度闸。

> ⚠️ **平台方已下场**：Claude Code 于 2026-02-05 随 Opus 4.6 发布 Agent Teams，
> 多 session 互相通信、共享任务、自协调。**编排这一层正在被商品化。**

**② Markdown 即事实源（撞得最狠）** —— [Backlog.md](https://github.com/MrLesk/Backlog.md)
几乎是「目录即状态机」（D19）的同款主张：任务是仓库里的 `.md`、YAML frontmatter、
看板就是目录、状态变更即文件改动、git 成为状态机，带验收标准与依赖，还有 MCP server。

社区已把这个模式提炼成话术：「`.md` 不再是文档，是人与 agent 之间的**协议层**」。
**方向被验证了，但不构成壁垒。**

**③ Agent 治理 / 护栏（我们最被低估的部分）** —— 行业共识与我们的设计惊人一致：
编排框架（LangGraph / CrewAI）**只管怎么跑，不管生产策略**——谁能批准写库、
token 预算多少、哪个动作要人闸。而「人闸不是瓶颈，是业务判断真正加值的质量控制点」
这句话，基本是宪法第五条（人本化）的英文版。

背景数字：Gartner 预测 2026 年 agent 软件支出达 2065 亿美元，
同时预计**超过 40% 的 agentic 部署会在生产中失败**。没人能回答为什么、怎么提前知道。

## 二、真正的资产：一份别人结构上拿不到的数据

`lifecycle.验收()` 里已经有这一段：

```js
const 误 = !通过 && 核查章.结论 === '通过' ? '漏判'
         : (通过 && 核查章.结论 === '不过' ? '误杀' : null);
if (误) ledger.score(root, { 线: '审检误判', 席: '核查', 单: id, 类型: 误 });
```

**每当机器判官与人的最终裁决不一致，系统自动记一笔。**
加上 H69 三条评分线（审检评执行 / 执行评拆单 / 项管评审检），
我们在**日常运营的副产品里持续生成一份带标签的判官准确率数据集**。

这个东西别人做不出来，不是技术难，是**结构上不具备**——
他们没有「人对同一份产出做最终裁决」这一步。没有那一步就没有 ground truth，
就永远只能说「我们的 agent 很好」而拿不出数字。

**而整个行业最缺的恰恰是数字。**

## 二·补 · 我们到底能回答哪个问题（论证核心）

「AI 审 AI 到底有没有用」不是一个问题，是三个。研究界只能答第一个的一部分：

| 问题 | 我们的数据源 | 研究界状态 |
|---|---|---|
| **拦住了什么** | `settleClose` 各拒绝分支命中数、QA 不过自修轮次 | 有（评测集上） |
| **放过 / 错杀了什么** | 「审检误判」线的漏判 / 误杀 | **几乎没有**——缺真实 ground truth |
| **值不值** | 预算账 × 返工轮次 | **没有**——没人在真实交付流上算过判官的账 |

第三个最没人碰：判官消耗 opus 档，拦下一张空壳省掉的是一轮返工——
**这笔账只有在真实生产里才存在**，评测集上根本没有「返工成本」这个概念。

### 我们的 ground truth 是什么，以及它不是什么

**是**：同一份产出上，机器判定与人最终裁决的分歧记录，自动生成、逐单落库。

**不是客观真理**。标签是「制作人的判断」，而公开研究给的人—人一致率只有 **81%**。
所以严格说我们测的是**「判官与这一位制作人的分歧率」**，换个制作人数字会变。

**这一点必须写进方法学，不能藏。** 但它不削弱结论，反而是最实用的口径——
**在生产环境里，签字的那个人就是标准**；评测集上的「正确答案」在真实工作流里不存在。

### 三个盲区

**① 共谋漏判**——判官说过、人也说过，但产出其实是坏的。即时标签里**完全不可见**。

> **解药已经在库里**：`推翻` 与 `返工自` 链。一张单走完全部审批点进了「完成」，
> 后来被 `推翻`（`lifecycle.推翻()` 强制写理由），或有新单挂 `返工自` 指向它——
> **那就是一次共谋漏判的延迟标签**。
> **即时标签 + 延迟标签 = 完整评估回路。据当日检索，没有公开研究具备这个结构。**

**② 幸存者偏差**——被三振打进「执行失败」却始终无人分诊的单，没有裁决记录。
要么把分诊做成必答，要么在指标里显式报告「未裁决占比」。

**③ 判官目前是「瞎判」的**——判官读的是回执文字，没有独立验证手段
（详见第四步「最该做的一件事」）。所以现在测出的数字，严格说是
**「纯 prompt 判官在真实工作流上的表现」**，而研究结论正是：这种形态
「没有任何工作证明能成功自我纠错」。

> 这反而是机会：**装上外部验证通道后再测一遍，两组数字一对比，
> 就是这个领域缺的那个实验**——有验证 vs 无验证，同一条产线、同一套裁决标准、
> 同一批工单类型。研究都在评测集上做，我们有的是真实交付流。

### 对外的一句话

> Ticketflow 不是又一个 agent 编排器。它是目前唯一能在**真实交付流**上、
> 用**人的最终裁决作标签**，持续测量「AI 审 AI」有效性的系统——
> 包括判官漏判率、误杀率、拦截了多少空壳交付、以及这道关卡的成本回报。
>
> 研究界在评测集上给出了判官与人 >80% 一致的上限；
> 我们回答的是它在**有成本、有返工、有人签字**的生产环境里，到底还剩多少。

分量全在「真实交付流」与「人的最终裁决作标签」两处——**别人结构上没有**，
不是不想做。

## 三、定位：做纪律层，不做编排层

> **给无人值守 agent 生产线用的纪律层。**

不是「又一个能并行跑 Claude Code 的看板」——那条赛道已经拥挤，且平台方已下场。

我们与别家 approval gate 的本质区别：**他们的是外挂的工作流节点，我们的是状态机的结构性属性**。
单子物理上进不了「完成」目录，除非人签了字。这不是配置，是形态。

编排在被商品化，治理还是空的。**往判官链、额度纪律、审批点走，比往看板和 worktree 走安全。**

## 四、benchmark 路径（三步）

### 第一步：把已有埋点变成公开指标

原料都在，缺的是口径定义与发布：

| 指标 | 现有数据源 |
|---|---|
| 判官**漏判率 / 误杀率** | `项管台账/评分.jsonl` 的「审检误判」线 |
| 一次通过率（无自修交付） | 工单 `自修次数` |
| 人闸触发率（多少单真需要人） | 待定夺 / 保留单占比 |
| 单位交付成本 | 预算账（施工令-021）+ 回执实耗 |
| 判官链故障率 | `判官重试上限` 计数、执行失败原因分布 |
| **空壳交付拦截率** | `settleClose` 各条拒绝分支的命中数 |

最后一条尤其值钱——**「如果没有判官链，多少空壳会混过去」**，
这是那些防御代码的量化价值，目前只存在于注释里的事故编号中。

### 第二步：出一个可复现的评测套件

一个标准参考仓库 + 一组标准工单，**含故意埋雷的**：需求含糊的、验收标准不可判定的、
会诱导 agent 越界的。任何编排器都能跑，输出同一组指标。

这一步是关键转折：**从「参赛者」变成「裁判」**。
别人评测自己的编排器时用我们的套件，我们的架构就成了参考实现。

### 第三步：公开事故档案

`settleClose` 的空输出/光板结论/结论无法判读、H63 软超时验尸、活尾巴取样、
死代理判红——每一条背后一个真实事故编号。整理成一份
**《无人值守 agent 的失效模式清单》**。

这是抄不走的可信度，因为它只能被烧出来。别人读完会发现自己踩过其中一半却没记录。

## 五、三个会杀死这个计划的东西

**① 仅 Windows。** 一个 benchmark 如果只能在 Windows 上跑，没人会采用。
**这是硬阻塞，不是优化项。**

**② 样本量。** 22 张单 + 一个游戏项目的量出不了统计意义；
判官误判率要几百张单才有说服力。没有捷径——
好处是**它跟正常干活是同一件事**，不需要额外投入，只需要时间与纪律。

**③ 既当裁判又当选手。** 指标定义若与产品绑死，没人信。
做法是把**指标规范**（一份 spec + 一个参考数据格式）与**实现**分开发布，
让别人能在自己的编排器上产出同格式数据。我们可以是第一个实现，**但不能是唯一可能的实现**。

## 六、如果只能做一件事

**先把「判官误判率」这一个指标做实、做久、公开。**

它同时满足四个条件：

1. 数据已经在流（零额外开发即可开始积累）；
2. 别人结构上拿不到；
3. 直接回答行业最痛的问题——**AI 审 AI 到底有没有用**；
4. 天然就是 benchmark：**一个数字，可比较，可复现**。

其余都可以往后排。

顺带一提：「studio 还是 platform」（见 [`工程队/议题-一个整机还是两个产品.md`](../工程队/议题-一个整机还是两个产品.md)）
在这个坐标系里不算要紧事——**两套 profile 共用一条判官链，反而让样本量翻倍**，
这本身就是选 B（一个整机两套 profile）的又一条理由。

## 附 · 「AI 审 AI」的研究现状（2026-08-08 检索）

四条结论，同时是对本设计的背书与警告：

1. **判官能达到人的水平，上限也就在那儿。** GPT-4 与人类评审一致率 **>80%**，
   而人—人一致率是 **81%**。两数重合意味着：**误判率的目标不该是 0**，
   接近 20% 的分歧是任务本身的噪声底。这给了 benchmark 一条参照线。
2. **自我审查基本无效，除非有外部反馈。** 综述结论：没有任何工作证明
   「用 prompt 让另一个 LLM 给反馈」能成功自纠。CRITIC 那条线把验证外包给工具
   （搜索 API 验事实、解释器验代码、分类器验毒性）。
3. **但「训练过的批评者 + 人」有用。** OpenAI CriticGPT：在自然产生的 LLM 代码错误上，
   模型批评有 **63%** 场合被偏好于人写的批评——**定位是帮人抓虫，不是替人拍板**。
4. **判官有三种量化偏见**：位置偏见最高 **75%**、冗长偏见、
   **自我偏好偏见 10–25%**（NeurIPS 2024 证明自我识别能力与自我偏好强度线性相关）。
   另有 93% 的团队在落地 LLM 判官时遇到困难。

### 对照本设计

| 我们的做法 | 研究对照 |
|---|---|
| **异厂对抗互审**（执行与核验分属不同厂商） | ✅ 直接消除自我偏好偏见（10–25%，且与自我识别线性相关）——不是审美选择，是结构性手段 |
| **人闸终审**（五个审批点、保留单只能人签） | ✅ 判官上限 ≈ 人—人一致率；CriticGPT 定位即「帮人抓虫」 |
| **红队立场卷制 · 击杀制**（H91，必须构造具体失败场景） | ✅ 对抗冗长偏见与泛泛而谈，逼判官产出可证伪断言 |
| **判官只读回执、无外部验证** | ❌ 正是结论 2 说「没有工作证明能成功」的形态。`settleClose` 的防御是补丁，不是根治 |
| **判官链无位置/顺序去偏** | ❌ 位置偏见可达 75%；两检制里初检结论进入深检上下文 = 锚定 |

**最该做的一件事**：给判官装上外部验证通道，从「读回执判断」变成 CRITIC 式「验证—再判定」。
QA 判官不该只读「测试全绿」这句话，而该自己去跑
（`tooling/` 下 `typecheck` / `unit` / `contract`，数字从结果文件根节点取）。
`套件/执行技能模板/post-work` 已写了这条纪律，**但那是给 agent 的约定，不是判官手里的工具——
约定可以被绕过，工具不能。**
