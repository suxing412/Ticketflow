## 第一章 · 总图

两个产品、一块公用地基、两片私域：

```
GitHub
├── suxing412/Ticketflow（公开）
│   ├── apps/studio/          ← 游戏工作流产线整机【suxin 方独有】
│   ├── apps/platform/        ← 通用软件开发平台整机【robinwang2 独有】（制作人 2026-08-09 拓扑正音：两产品一仓）
│   ├── packages/             ← 公用件唯一家【双签共建】
│   ├── 套件/                  ← 已迁 packages，只剩转发壳【下次换装后退役】
│   ├── 工程队/                ← suxin 方施工令档案
│   └── docs/                 ← 协作文书 + docs/信道/ 双向信箱【共用】
├── suxing412/AI-DevPlatform（私仓，授权 robinwang2）
│   └── robinwang2 的业务数据仓 ← 与 AI-GameStudio 对称：存他用平台开发项目时的项目数据/配置，产品代码不在这里
├── D:\GitHub\AI-GameStudio（suxin 方私仓，永不公开）
│   └── 协议库正本/工单数据/配置(含密钥)/白夜馆 ← 业务与账本
└── （robinwang2 自己的业务私仓，与上对称，自便）
```

**切分判据一句话**：「不知道自己在开发什么」的层公用（执行、监视、评审、计费、供应商接入）；「知道业务是什么」的层各归各家（流程语义、编制/角色、提示词、UI、知识库）。

**并排克隆约定**：两仓必须并排放（如 `D:\GitHub\Ticketflow` + `D:\GitHub\AI-DevPlatform`），platform 以相对路径消费 packages；环境变量 `TICKETFLOW_HOME` 可覆盖。

## 第二章 · apps/studio——游戏工作流产线整机（suxin 方）

一台 Electron 单机驾驶舱：目录即状态机的工单流水线，多 agent CLI（claude/codex/deepseek）按编制领单干活，制作人只握人闸（签字/拍板/废弃）。

### 2.1 调度心脏（H49 状态机）

| 模块 | 职责 |
|---|---|
| `lib/lifecycle.js` | 工单生命周期：草稿→待投→在途→质检→待验收→初检→深检/核查→完成；仲裁/上呈/返修同号回炉；挂起族（原位冻结/解挂/全树连带） |
| `lib/gates.js` | 闸门：人闸（制作人签字位）/机闸（测试、格式）/额度闸 |
| `lib/pool.js` | 工单池与领单（按编制池序 claim） |
| `lib/stages.js` | 阶段定义与流转规则 |
| `lib/runner.js` | 执行器循环：CLI 进程拉起、tail 兼收 stdout/stderr、软超时验尸、判官失败不打整单、空输出不作数、候选链降级。**实战加固最厚的一件，未来 packages/core 头号候选（按需抽取，不预抽）** |
| `lib/recommend.js` `lib/preflight.js` | 派单前置检查（验收方式枚举、依据链、活编制职能表） |
| `lib/concurrency.js` `lib/quota.js` | 并发配额与各池额度闸 |

### 2.2 项管与知识

| 模块 | 职责 |
|---|---|
| `lib/pm/` | 项管大脑（起草工单六件套）+ 巡检狗（零派发/零输出/打点停滞/挂起中告警） |
| `lib/wiki.js` `lib/docs.js` | 知识总库五区：设计事实词条（溯源链）/策划案（定案·草案·决策记录）/调研方案/技术方案/美术标杆 |
| `lib/codoc.js` | 协同策划文档：块级作者标记，保存即 git 页史 |
| `lib/roster.js` | 编制（一职能一行池序） |
| `lib/journal.js` `lib/ledger.js` `lib/report.js` | 台账/流水/消耗报表 |

### 2.3 整机壳与周边

- `server.js`（HTTP :4270 + 全部 /api）、`main.js`（Electron）、`public/`（总览/工单/树形/在途/决策台/流程管线甘特/报表/项管/wiki 全套 UI）。
- `lib/netprobe.js` / `lib/creds.js`(DPAPI) / `lib/setup.js` — robinwang2 贡献、按界碑归 studio 养。
- `lib/budget.js` — **迁出中**：本体归 `packages/budget`（robinwang2 主导），studio 留薄接线。
- 测试：`npm test` 35 套件 334 例，全绿是入库硬门槛。

### 2.4 studio 的私域依赖

studio 开机读 `AI-GameStudio\监制台\studio.config.json`（编制/阈值/白名单/密钥），工单数据也在私仓——**公开仓里只有机器，没有业务**。克隆 Ticketflow 后 studio 开不了机属正常（缺私域配置），无需修复。

## 第四章 · apps/platform——通用软件开发平台（robinwang2；2026-08-09 拓扑正音后正本回归本仓）

### 4.1 开机手册

正本：本仓 `apps/platform/`（robinwang2 全权，CODEOWNERS 划界）。`github.com/suxing412/AI-DevPlatform` 转为其**业务数据仓**（对称 AI-GameStudio）。注意：正本回归单仓后，`../Ticketflow` 并排解析需改为仓内相对（`../../packages`），公用件.js 的解析序由 robinwang2 自定。

**方式一 · 源码开机**：

```
git clone <Ticketflow>      → D:\GitHub\Ticketflow      （公用件来源，并排）
git clone <AI-DevPlatform>  → D:\GitHub\AI-DevPlatform
cd AI-DevPlatform && npm install && npm start
浏览器 http://127.0.0.1:4370
```

零第三方依赖；`TICKETFLOW_HOME` 环境变量可覆盖并排路径。

**方式二 · 桌面观览壳（可选件）**：双击 `AI-DevPlatform 0.1.0.exe`（portable 单文件，内嵌同一台 server）。开发态 `npm run desktop` 同效。注意：打包态并排克隆约定失效，未设 `TICKETFLOW_HOME` 时按 `D:\GitHub\Ticketflow` 兜底（main.js 内一行，换机自改）。自行重打包：装 devDependencies `electron@30.5.1` + `electron-builder@24.13.3` 后 `npm run dist`（Ticketflow 侧打包曾复用 apps/studio 的 electron 本地分发以免镜像下载，见 `-c.electronDist` 用法）。

### 4.2 出厂清单（交钥匙壳已含）

- `server.js`：最小 HTTP（:4370）——/api/health、/api/watchtower（在岗灯数据）、/api/providers（枚举）、/api/providers/echo（**桩调用**，物理不引入 child_process，发不起真实 CLI）；
- `public/index.html`：一页仪表盘——providers 表（含桩测按钮）、**瞭望塔在岗灯**（心跳戳 45s 新鲜阈值，绿=在岗/红=离岗+拉起命令提示）、未读账本；
- `lib/`：orchestration/routing/workspace/toolchain/review-opinion 五件原零件（byte 级一致迁入）+ `角色协议模板/` 六份；
- 瞭望塔预装：`config/瞭望塔.config.json`（本方名=robinwang2，远端盯 ../Ticketflow，信箱分拣已启用）+ `scripts/watchtower.js` 启动器（`npm run watchtower`，`watchtower:install` 装开机自启，任务名 AI-DevPlatform瞭望塔）；
- `docs/`：README 开机手册与边界宣言、边界与协作.md、接线说明.md（怎么让 Claude Code 被信箱唤醒）；
- `main.js` 观览壳（Electron 入口 + portable 打包配置，可选件——要不要长成正式桌面壳由 robinwang2 定）。

### 4.4 已知注意事项

## 第五章 · 信箱协议（双向唤醒信道）

- 信箱本体：Ticketflow `docs/信道/收-总监/` 与 `docs/信道/收-robinwang2/`，文书格式见 `docs/信道/README.md`，**git push 即投递**。
- 两端各跑一座瞭望塔：远端信道每 5 分钟 fetch，寄给自己的→急+弹通知+唤醒常驻 Claude Code 会话（Monitor 盯统一流水，见接线说明）；寄给对方的→只记流水（不自吵）。
- 特性：存转信箱——双方无需同时在线，消息不丢；单程延迟最坏 ~5 分钟（间隔可调）；断网静默容错、恢复即续；`-c core.quotepath=false` 已内置保中文文件名识别。
- 运维纪律（各自负责）：守护开机自启 + 常驻会话。suxin 侧现网守护要到下次换装才启用分拣规则。

**信道不可用时的兜底渠道**：微信/邮件皆可，恢复后补归档文书（2026-08-09 增补，案源：收货回执信道死结）。

## 第六章 · 协作协议全文（五条口径 + core 路线)

### 6.1 五条口径（制作人 2026-08-08 逐条拍板）

1. **公用件唯一家 = packages/**：node 包规范（package.json+测试+README）。存量套件已全部迁入。
2. **预算池**：本体 `packages/budget` 归 robinwang2 主导；studio 薄接线归 suxin 方。现 feat/budget-gate 分支按此口径调整后提 PR。
3. **动对方 app 先对齐**：改对方整机内文件，先发一页方案获批再动（双向同规）；packages/ 走正常 PR 双审。
4. **施工令命名空间**：suxin 方 `施工令-NNN`，robinwang2 方 `协-NNN`，序列各自涨。
5. **PR 流程**：作者提 PR → 对方批准 → 作者合并；分支保护强制 1 批准；测试红=先报告。

### 6.2 packages/core 生长路线

不预抽、按需抽：platform 补整机时第一个真实需要的共享件先抽（大概率 runner 或 lifecycle 与 core/store）。robinwang2 那份「重构分支改动 12 文件」实测清单即抽取范围候选（core/{config,state,store}、gates、pool、lifecycle、recommend、runner、stages）。每次抽取一张双签施工令（一方出方案另一方评审），抽完两侧回归全绿才算落地。执行器的实战加固（软超时验尸/判官失败隔离/空输出不作数/活尾巴取样）只维护这一份。
