### ② 起法改了，连带面必须一起改（否则要件一是自伤）

`--include-partial-messages` 会把增量事件（`type=stream_event`）也灌进 stdout，两处旧代码扛不住：

- **`out` 会被增量撑爆**。`out` 有 800KB 上限、超了截头，而 `extractClaudeText/settleClose` 读的就是它——
  流量涨几倍等于把「真报告被截掉」的概率也涨几倍。
- **活尾巴会缩成一个标点**。旧样 `entry.tail = 最后一个 "text":"…" 匹配`，加了增量后最后一个匹配
  就是最后一片 delta（常常是「。」）。UI 显示与 H63 软超时验尸都读它。

故在 stdout 入口加**行分拣**（`流分拣器/分派`，纯函数、已导出、有单测）：

| 路 | 去向 | 为什么 |
|---|---|---|
| 主流（非增量整行） | 拼进 `out` | `extractClaudeText/settleClose` 读到的东西与 047 前**同形**，上限也不被增量占用 |
| 计量细流（含 `usage` 的整行） | 单独留一份喂 `usageOf` | `out` 截的是头，而 usage 行截掉就永远补不回来——账不能跟着显示缓冲一起丢 |
| 增量文本片 | 只更新活尾巴，**不留存** | 尾巴 = 最近整块文本 + 其后到达的增量片，跟着字走还能读成句 |

对账的口径影响：**零**。增量事件的 usage 挂在 `e.event.usage` 上，`budget.usageOf` 只认
`e.usage / e.message.usage`——它本来就不数增量行（测试里单独钉了这一条，见 §一.1）。

顺带修的一处失实：`cliPool`（记账用的池名）旧样是 `kind === '执行' ? poolName : 'claude'`，
于是**二线 LLM 档的初检**（走 `两检.池`，默认 deepseek）会把账记到 claude 头上。
流水失实事小，记错池事大——判超会掐错池。已改为 `执行/初检 用真池名，判官三席才是 claude`。

### ③ 一条口径观察：`输出 = Σ` 会把 `result` 事件重复计一遍

信 §二 写的是 `输出 = Σ(output_tokens)`，而 claude CLI 的收尾 `result` 事件带的是**整场会话的汇总 usage**。
逐行累加时它会和前面每条 assistant 消息的 output 叠一次——**样例里 120 + 780 + 900 = 1800，真实输出是 900**。

本令**照信抄，一个字没改**（口径是两边对账的公约数，单方面改比偏差本身更危险）。
方向上偏保守（多算 ≈ 一倍 → 保险丝早刹，不会漏刹），但这是"生产会被提前掐"的那种偏保守，
建议总监向 robinwang2 对一次：他们执行器侧是不是也这么叠，还是 `result` 那条另有处置。
一旦确认，改动只在 `packages/budget/budget.js · usageOf` 一处，两边同步即可。
