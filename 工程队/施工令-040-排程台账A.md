# 施工令-040 · 排程台账 A（实体+迁移+CAS+状态机）

案源：2026-08-11 点名巡礼主案（白夜馆/2026-08-11-点名巡礼-排程可见性.md §2/§4/§6）——制作人「监制台看不到后续的队列工作」；方案经 codex+deepseek 红队 11 杀修订为 v2，本令实装 v2 的后端半（Q1）。消费接线（流程页/总览/晨晚报）在 Q2（施工令-041），本令**不动前端**。

## 目标

系统内新增「排程台账」实体：承载**计划粒**（尚未成单的批次计划项），使「接下来要做什么」成为系统数据而非会话记忆。

## 实装要求（红队 v2 口径，逐条为验收项）

1. **存储**：`lib/pm/schedule.js` + 部署区 `排程账.jsonl`——事件日志式**只追加**（每事件含 `粒ID/事件类型/字段变更/版本号/时刻/操作者`），读取时折叠为现态。禁覆盖写。
2. **计划粒结构**：`粒ID`（UUID，不可变）、`批`、`序`、`题`、`管线`、`状态`、`依赖:[{ref(粒ID|单号), 规则:'全部完成'|'任一完成'}]`、`池衡建议`、`预估单元`、`来源`（文档§引用）、`单号`（已成单后回填）。
3. **状态机**：`计划→起草中→已成单→完成`；任意前置态→`撤销`；**已成单不可直接撤销**（须先收回对应工单，由调用方保证并在 API 层校验拒绝）。非法转移一律拒绝并留痕。
4. **并发控制**：写 API 带 `预期版本`（CAS）——版本不符拒绝后写，返回现态供重试；appendFileSync 单进程内串行即可，但 API 层必须显式校验版本。
5. **API**：`GET /api/schedule`（现态列表，按批/序）; `POST /api/schedule/登记`（整批登记，总监/项管）; `POST /api/schedule/转移`（状态转移，带预期版本）; `POST /api/schedule/调整`（改序/依赖/池衡，带预期版本，H99 项管域）。
6. **H57 挂接**：`/api/pm/draft` 请求体可带 `粒ID`；起草完成落草稿时把粒状态转「起草中」，定稿放行后由 lifecycle 在派发时转「已成单」并回填单号（挂接点在 lifecycle/journal 已有事件流上加钩，不重构 Pump/派发结构）。工单 frontmatter 增可选字段 `粒ID`。
7. **首次迁移**：`scripts/migrate-schedule.js`——读 `D:/GitHub/TK/Docs/SLG/调研方案/汉代地图修缮总清单.md` §3 批次表（批C 五幅面单/批D 两项/批E 一项）与巡礼报告 §六 Q1-Q6 队列，生成初始计划粒（来源引用落准确章节）；已在途/完成的批次项（批0/A/B）生成为对应终态并回填已知单号（TK-127/128/129/130/131/132/134）。迁移幂等（重跑不重复——以 `来源+题` 判重）。
8. **测试**：`test/schedule.test.js`——状态机全转移矩阵（合法/非法各测）、CAS 冲突拒写、事件折叠正确性、迁移幂等、挂接钩子（模拟 draft→派发链）。node 直跑全绿。
9. **不做**：任何前端改动；晨晚报接线；H99 额度感知（另令）。
