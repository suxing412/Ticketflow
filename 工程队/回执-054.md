## 三、三处自主判断（都写在代码注释里，便于日后追责）

**① 落账口径抽成 `wake.onCutResult` 导出函数，而不是留在回调里。**
令面写区点名 `wake.js`（切单链）。原实现是 `brain.cut` 回调里的两行内联，而回调在 `opts.test`
下**根本不跑**——要件4 的三分支测试无从下手。抽成导出函数后三分支各一格纯函数测试，
且两条调用链共用一份口径（见②）。

**② `server.js` 手工切单 API 改调同一函数（外溢一处，3 行）。**
`/api/pm/cut` 此前自带一份一模一样的回调。不改它，「拒切候期」就会在自动链合法、在总监手工
点「切单」时被记成失败——同一个模型判断，两个出口，纯属埋雷。改成
`(r) => require('./lib/pm/wake').onCutResult(ROOT, String(父单), r)`，落账实现从此只此一份。

**③ 判语要看得见：`chain.js` + `app.js` 各一处（外溢两处）。**
TK-146 是「双料病」——判语没存档，且就算存了也没有渲染分支。故：`chain.js` 关键事件白名单
加 `切单候期` 并给一条 case（站=切单，文=「项管拒切候期：<理由>」，因=「复切时机：…」，
**链上一个「失败」字都不出现**）；`app.js` 的 `pmEventLine` 加一条渲染分支（通用分支只画得出
「切单候期：P-1」，理由与复切时机全丢）+ KEY 集合登记（否则它会混进「详细流水」而不是关键汇报）。
两处都是纯展示，无判断逻辑，`chain.js` 的纯读铁律测试（字节级零变化）照旧绿。
