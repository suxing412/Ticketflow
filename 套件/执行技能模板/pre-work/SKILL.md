# 开工检查（领单后第一动作，跳过=违纪）

## 一、评估可行性（H61 评估回呈制）

逐项判定，任何一项不满足 → 不要开工，回执只写一段 `## 评估回呈`（做不了的原因 + 缺什么 + 处置建议），立即交单结束。评估回呈不算失败。

1. **写区**：工单要改的文件全部落在本职能章程的写区内？（装配单不改 Scripts/Tests；程序单不存场景——历史事故：TK-76 装配单实需改码，三轮自修实为无权动手）
2. **工具**：工单点名的通道在 `node tools/enginectl.js 探测` 的清单里？（历史事故：TK-71 点名的通道未广告，误判缺失）
3. **前置**：依赖单的回执/产物真实在位？（装配包已注入上游回执，核对与工作区实物一致）
4. **规模**：预计时间内做得完？光测试套件就要超预算的，如实回呈。

## 二、环境体检

1. `git status --porcelain` 留快照进回执——分清「本单改动」与「领单时遗留」（历史事故：TK-75/76 跨单遗留污染定责困难）。
2. `Temp/UnityLockfile`、`.enginectl-lock` 残留即在回执报告（孤儿锁案）。
3. 返修单（frontmatter 有 返修轮）：先读回执里前几轮的分节史，明确本轮只补什么。

## 三、定测试基线

跑一次与本单相关的测试（或读最近一次 `enginectl-results.xml` 并注明时间戳），记录**既有红灯清单**——这是「本单没有引入新失败」的唯一证据分界线。

## 四、开工声明

回执开头固定三行：评估结论（可做/回呈）、基线（total/passed/failed + 既有红灯名单）、计划步骤（≤5 条）。

## 五、进度打点（软契约，2026-08-06 起）

开工声明后，把计划步骤当刻度：**每完成一步，向输出流单独打一行** `[进度 k/n 一句话]`（k=已完成步数，n=计划总步数，如 `[进度 2/5 常量搬家完成]`）。监制台据此显示实时进度并做停滞预警。规矩三条：①打点行独占一行原样输出，别嵌进其他文字；②只在真完成时打，不预报；③忘打不判罚（缺打点时监制台回落时间估算），但打了就要真——假打点按回执失实处理。长等待（如后台跑测试）期间每隔几分钟输出一行普通文字说明在等什么，防止被判停滞。
