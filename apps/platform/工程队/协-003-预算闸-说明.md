# 预算闸说明（施工令-021 配套）

> 设计说明与用法。**为什么要有它**、**怎么接进去的**、**怎么配**、**边界在哪**。
> 规格正本见 [`施工令-021-预算闸.md`](施工令-021-预算闸.md)。

---

## 一、它补的是哪个洞

2026-08-08 落了凭据托管，「套餐用完降级到 key」这条路通了——池序顺位即路由，
`claude` 池冻结就自动落到 `claude-key`，零新机制。

**但降级之后没有任何刹车。**

现有的成本闸全部建立在同一个前提上：**订阅有一个会重置的用量窗口**。

| 闸 | 判据来源 |
|---|---|
| `执行池.*.阈值` / `周阈值` | `quota.js` 从订阅端点读回的 5h / 周用量百分比 |
| `额度.沟通保留`（沟通护城河） | 同上 |

API key 是**按量计费，没有这个窗口**。`gates.poolLock` 对 key 池永远算不出 `fivePct`，
于是 `locked` 恒为 false。结论：

> 降级一旦触发，**跑多少烧多少**，唯一止损手段是人盯着屏幕。

这是不能上生产的状态。预算闸就是给按量池补的那根保险丝。

## 二、怎么接进去的（本单最关键的一个决定）

**没有改 `dispatch.poolFrozen` 的签名。**

`poolFrozen(cfg, gatesInfo, poolName)` 是全系统判断「这个池现在能不能派单」的唯一入口，
被三处消费：派发路由（`routePool`）、编制快照可用性（`/api/pm/roster`）、UI 闸态（`/api/gates`）。

改它的签名意味着三处调用点、若干测试、以及所有间接调用者一起动。所以换了个方向：

```
budget.冻结池(cfg, root)  →  { 'claude-key': { locked: true, reason: '…' } }
                                        ↓
budget.并入(gatesInfo, 冻结)  →  由调用方合进已有的额度锁结果
                                        ↓
poolFrozen 一个字不改，自动认它
```

产出结构与 `gates.poolLock` 的输出**对齐**（都是 `{locked, reason}`），于是：

- 池序降级自动生效（超预算的 key 池会被 `routePool` 顺位绕开）；
- 编制快照的「可用/止派」自动跟着变；
- UI 与调度**同一把尺**，不会各算各的。

零额外接线。这是整单唯一值得记住的设计。

## 三、计量口径

### 三列分开，合计不含缓存

```js
{ 输入, 缓存, 输出 }   // token 合计 = 输入 + 输出，缓存单独留数
```

缓存读的计费约为常价 1/10。混进合计会**虚胖离群**——`pm/brain.js` 已经踩过这个坑
（「起草 57.9 万 token」案），这里沿用同一教训。

`输入`/`缓存` 取流中最大值（它们是累计量），`输出` 累加（它是增量）。

### 账本

`<工作区根>/预算账.jsonl`，只追加，一行一次会话：

```json
{"t":"2026-08-08T13:02:11.000Z","池":"claude-key","单":"TK-42","输入":12000,"缓存":88000,"输出":900}
```

明文即事实源，与 journal 同纪律。坏行丢弃不抛，缺文件返空汇总。

### 窗口

当日（`YYYY-MM-DD`）与当月（`YYYY-MM`）两个窗口各自累计，跨月不串。

## 四、怎么配

```json
"预算": {
  "池": {
    "claude-key": { "日token": 2000000, "月额": 80 },
    "deepseek":   { "日额": 2 }
  },
  "价目": {
    "claude-key": { "输入": 3, "输出": 15 }
  }
}
```

- **`日token` / `月token`** —— token 上限，不需要价目表就能用。
- **`日额` / `月额`** —— 金额上限，需要配 `价目` 才生效。
- **两种可并存，任一触线即超。**
- `价目` 单位是**每百万 token 的金额**；`缓存` 不写时默认按输入价的 1/10 估。

### 三条硬规矩

1. **未配预算的池永不被本闸冻结。** 不配 = 不管，绝不臆造上限。
2. **算不出费用就不许判超。** 配了 `日额` 但没配 `价目` → 金额那一路自然失效，
   只剩 token 口径，不会拿一个瞎猜的数字去掐派发。
3. **`≥` 而非 `>`。** 用到线上就算超，保守一格。

## 五、边界（刻意不做的）

- **不碰订阅侧。** `gates.poolLock` 与 `quota.js` 一字未改。订阅归订阅、按量归按量，
  两套判据并存，不做语义合并。
- **不是财务系统。** 厂商账单口径各异，本模块只求偏保守的估算。
  它是**保险丝**，不是对账工具。
- **不做 UI。** 参数页的预算卡片划在范围外（另单）。现在只有 API 与判据。

## 六、已知限制：codex 计量不到

`budget.usageOf()` 解析的是 stream-json 事件流里的 usage 字段——**只有 claude 家族有**。
codex 走纯文本流，取不到 usage，所以 codex 池的账永远是 0，预算闸对它形同虚设。

这不是遗漏，是同一天实测出的连锁事实：

> codex CLI **完全无视** `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN`——
> 注入垃圾令牌 + 非法 base 后 `codex exec` 仍退出 0 正常作答，它走自己的 `~/.codex` 登录态。

所以给 codex 池配 key 本身就是**双重错误且完全静默**：
① 你以为在按量池上跑，实际在烧订阅；② 预算闸取不到 usage，永不触发。

处置是在 `runner` 侧**响亮拒派**：`凭据Of()` 对 codex 池一律返回 `null`，
`startWork` 检测到 codex 池配了托管 key/内联兼容段就直接判执行失败并说明原因。
**宁可响亮地拒派，不要静默地跑错池。**

（这条知识已同步进 `packages/providers/README.md` 的「现网调用约定」节——
它本质上是 provider 适配层的事实，不该只活在 studio 的注释里。）

## 七、测试

`test/budget.test.js` **14 例**，其中三条是红线：

| 用例 | 守的是什么 |
|---|---|
| 未配预算的池永不被冻结 | 不臆造上限 |
| 冻结结构可直接喂 `poolFrozen` | 本单零接线的全部前提，这条不过等于没做 |
| **超预算的 key 池会被池序绕开** | 端到端实证：套餐冻结→落 key 池→key 烧超→顺位到 codex |

最后一条是整单唯一的价值证明——保险丝要真的能断电才算保险丝。

本机全量：**35/36 套件、302 用例**。唯一的红是 `runner.test.js` 的时序碎测试
（写死 40ms 假设、本机子进程 ~52ms 才出字节），协作回执已认领为对方本周修，非本单引入。
