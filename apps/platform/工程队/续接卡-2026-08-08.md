## 四、两条必须记住的事实

**① codex 完全无视 `ANTHROPIC_*` 环境变量**（2026-08-08 实测：注入垃圾令牌 + 非法 base
后 `codex exec` 仍退出 0 正常作答）。给 codex 池配 key 会**双重错误且完全静默**——
以为在按量池跑实际烧订阅，且预算闸取不到 usage 永不触发。已在 runner 侧响亮拒派，
知识已同步进 `packages/providers/README.md`。
**命名陷阱**：`resolveCli` 只把恰好叫 `codex` 的池路由到 codex CLI，`codex-key` 走 claude CLI。

**② 分支保护的死结**（对方即将开启，开之前务必先说）：
若勾了全局 "Require approvals: 1"，你自己全权区的 PR 会卡死——GitHub 不把 PR 作者
分配给自己的 PR，于是没人能批。正确配法是勾 "Require review from Code Owners"
而不设全局 approvals 下限，或对自己全权区保留 bypass。**对方的 studio PR 同样会撞上。**

## 五、预算闸的两个技术要点

**接入方式**：**没改 `dispatch.poolFrozen` 签名**。`budget.冻结池()` 产出
`{locked, reason}`（与 `gates.poolLock` 对齐），由调用方 `budget.并入()` 合进 `gatesInfo`，
于是池序降级、编制快照、UI 三处自动跟着走，零额外接线。

**未来归属**：`budget.js` 零 studio 引用（只 require `fs`/`path`），而 `packages/core/README.md`
把「双闸 / 额度纪律」列在共享地基范围内——**它是 core 抽取的首选样本**。
现在没抽，是因为同一份 README 说「由 platform 的实际消费方式决定包形状，避免闭门造 API」，
而它目前只有一个消费者。缝已经画好了：
**计量与判据（`记`/`汇总`/`估费`/`超预算`，纯函数）→ core；执行点（`冻结池`/`并入`）→ 各产品自己。**
等 platform 接第二个消费者时，那就是抽取的自然触发点。

## 五点五、**待拍板的上游议题**：platform 是产品还是 profile？

迁入过程中查出：原重构分支相对 main 是 **29 新增 + 29 修改**，而修改的是 studio 整机
（`core/{config,state,store}` / `gates` / `pool` / `lifecycle` / `recommend` / `runner` / `staff` / `stages` / `main.js`）。
`apps/platform/` 里**没有 server.js / main.js / public/**——**它不是独立 app，是被改造过的 studio**。

于是三条路：A 给 platform 补整机 / **B 让 studio 支持 profile 切换**（重构分支本来的做法，只是没做成开关）/ C 维持零件盒。

**「预算闸归属」是这件事的下游**，没有独立答案：选 B 则归属问题自动消失（本来就在共用层），
选 A 则必须进 core，选 C 则维持现状。所以讨论顺序必须是
**① 一个整机还是两个 → ② core 抽哪些 → ③ 预算闸归属**，反过来会卡住。

**附赠**：`packages/core/README.md` 说「由 platform 的实际消费方式决定包形状」——
那 12 个被改的文件就是这个问题的实证答案，抽 core 时照单谈即可。
（注意 `staff.js` 已随 H85 去岗位化删除、由 `roster.js` 取代，platform 的角色体系要重新落到每职能一行的模型上。）

完整论据见 [议题-一个整机还是两个产品](议题-一个整机还是两个产品.md)（可直接发给同伴）。
