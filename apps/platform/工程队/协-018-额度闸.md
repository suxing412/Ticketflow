# 协-018 · 额度闸接线（消费 packages/quota）

- 提出：2026-08-23
- 背景来源：信道 `docs/信道/收-robinwang2/2026-08-18-总监-quota已落包.md`
- 归属：我方（robinwang2）。包是对方主笔，**接线归我方**（budget 时的默契照旧）

## 背景

`packages/quota` 于 2026-08-18 落包（施工令-059，应我方请求提取）。包只收**解读**那一半：
窗口解析、百分比、label、重置时刻、守门判定 `gateOf`，纯函数零 I/O，取数归调用方。
落包五天，platform 侧**零消费**——全仓 grep `quota` 只命中 `lib/计费.js` 里两条错误串正则。

而这个洞不是「少了个功能」，是**订阅池现在根本没有窗口刹车**：

- `packages/budget` README 自己写的定位是「额度锁的**按量计费孪生**」——它守的是 token 上限；
- platform 的 `派单.冻结情况` 只并入了 budget 的冻结结果，**没有任何一处读订阅窗口**；
- 于是 `config/预算.local.json` 现在这样（原文注释，我方自己写的）：

  > "codex 取不到 usage，配上限也不会累计……给它配上限只是为了过第三道闸，
  > 实际刹车对 codex 无效，这一点要清醒。"

  **给订阅池配 token 上限是在演戏**：codex 的用量根本不进账本，claude 的 token 数
  也不是订阅窗口的计量单位。真正会把人停摆几小时的是「5h 窗口烧穿」，
  而那个数今天在 platform 这边一次都没被读过。

## 范围

① `lib/额度闸.js`（**纯，可被 server 引**）：消费 `packages/quota`，把快照判成「哪些池现在不许派」。
② `lib/额度取数.js`（**有 `child_process`，只准执行器引**）：codex `app-server` / claude OAuth usage
   两个取数口 + 节流纪律 + 落盘快照。
③ 取数与判定**分进程**：执行器定期取数落 `journal/额度快照.json`，server 与 `派单` 只读盘。
   这是为了守住既有的桩模式断言——`server.js` 的依赖闭包不得出现 `child_process`。
④ 判据接入**不改 `冻结情况` 签名**：额度冻结与预算冻结并进同一个 `挡` map，
   于是池序降级、编制快照可用性、`/tick` 归因三处自动跟着走，零额外接线（照 budget 先例）。
⑤ **按计费模式分闸**：`计费.模式 === 订阅` 的池走额度窗口闸，`api` 池走 budget token 闸，
   `本地` 池不闸。两套判据并存，不做语义合并。
⑥ `GET /api/额度` + 驾驶舱一张卡：窗口百分比、重置时刻、**盲区如实标出**。
⑦ `test/额度契约.test.js`：判定层 + 接线层（含闭包断言）。

## 不要做

- **不改 `packages/quota` 一个字**。它是双签共建的正本、对方主笔。我方接线时发现的口径出入
  （见「已知口径出入」）走信道回信提，不单方面动包。
- **不动闸③（真跑四闸里的「该池配了上限」）**。今天订阅池没配 `预算.池.<池>` 就 403，
  这个方向是保守的，不为了顺手而改钱路上的闸。额度闸是**与预算闸同级的第五道**，
  加在 `冻结情况` 里，不替换任何现有闸门。
- **不刷新 claude 的 OAuth token**（见下「一条硬纪律」）。
- 不做额度的历史曲线 / 趋势图（本单只出当下快照与判据）。
- 不引入新依赖。

## 一条硬纪律：platform 只读 `.credentials.json`，绝不写

studio 的 `lib/quota.js` 在 accessToken 快过期时会走 refresh 流程，**并把新 token
（含轮换后的 refresh_token）原子写回 `~/.claude/.credentials.json`**。

两个产品跑在同一台机器、同一个 Claude 账号上。如果 platform 也刷：

1. refresh_token 是**轮换**的——谁后刷，谁手里的旧 refresh 就作废。两边互相把对方踢下线，
   而表现是「额度偶尔读不到」，查起来极难；
2. OAuth 用量端点有**账号级限流**（对方 2026-07-11 吃过两次 429，窗口长达小时级）。
   两个产品各有各的节流盘、互不知情，合起来的实际频率是两倍。

所以本单定死：**platform 只读 accessToken，过期就当读不到（fail-open + 标盲区），
刷新永远归 studio 那一侧。** 节流间隔另取更保守的默认值（600s，studio 是 300s）。

## 验收标准

□ `lib/额度闸.js` 纯：不引 `child_process`、不发请求；判定整块来自 `packages/quota.gateOf`
□ `server.js` 依赖闭包**仍然**零 `child_process`（既有断言不许因本单变红）
□ 订阅池窗口越线 → `冻结情况.挡` 里出现该池，且 `/api/roster` 的可用性、`/tick` 的跳过归因同步跟着变
□ `api` 池不受额度闸影响（它归 budget）；`本地` 池永不被额度闸冻结
□ 快照缺失 / 过期 / 解读件失效 → **fail-open 放行**，但三处都要吭声：接口 `盲区` 字段、
  界面标注、执行器控制台一行。绝不把「读不到」显示成「额度充足」
□ claude 双窗能进 `gateOf`（本仓归一化，见下）
□ `npm test` 全绿（既有 224 项一条不许红）

## 已知口径出入（接线时发现，走信道回信，不在本单改包）

1. **`gateOf` 只吃 codex 形状**。它读的是 `rl.primary` / `rl.secondary`，而 claude 快照是
   `{fiveHour, sevenDay}`——claude 池**进不了这个判定**。studio 那边没撞上是因为它的
   `gates.poolLock` 走 `windowsOf` / `claudeWindows` + 每池阈值，压根不经过 `gateOf`。
   我方在 `lib/额度闸.归一()` 里把 claude 双窗映射成 `primary(300min)/secondary(10080min)` 喂进去。
   建议这段归一化进包（`claudeAsRateLimits`），否则两个消费方各写一遍，判定还是会分叉。
2. **两套阈值口径并存**（包 README 已如实记）。platform 选**全局 `cfg.quota` 那一套**（`gateOf`），
   不做每池阈值——池的差异在我方这边由「计费模式」表达，不由阈值表达。
3. `fmtReset` 走本地时区、`gateOf` 的 fail-open 红线——两条都合用，无异议。
