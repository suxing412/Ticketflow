## 零、先说清楚这张令的性质

前四张（#36 #38 #39 #43/#44）改的都是**平台自己怎么想**：路径怎么解析、模块怎么接线、
门禁怎么设、工单怎么落盘。全程零真实进程、零计费、零外部副作用。

**这一张不一样。批准它意味着三件此前一直没有的事：**

1. **平台会真的花钱。** 执行 = 拉起 claude/codex CLI，按 token 计费。
2. **平台会真的改文件。** AI agent 在工作区里写代码、跑命令。
3. **平台会真的动 git。** 检查点提交、合并回主线。

`server.js` 头上那句「任何路径都发不起真实 CLI 进程，零计费」——**这张令执行完，
对 server.js 本身仍然成立**（见决定 1），但对「平台」这个整体不再成立。

这是从「壳」变成「产品」的真正那一步。**请按这个量级审。**

## 二、本令决定的（三项）

### 决定 1 · 执行器单独一个进程

沿用工作区服务立下的先例：**能起进程的能力不进 `server.js` 的依赖闭包**。

新增 `scripts/执行器.js`，独立端口（默认 4372），自己带门禁。`server.js` 只经 http 转发。
于是那条传递闭包断言继续原封不动守着 server——**这次也不需要任何例外**。

为什么不复用工作区服务：它的能力面是 git，执行器的能力面是「拉起任意 AI CLI」。
两者风险量级不同，混在一个进程里，将来想单独关掉其中一个就办不到了。

### 决定 2 · 移植 studio runner 的四条实战加固

`docs/仓库总说明书.md` 2.1 把 `lib/runner.js` 记为「实战加固最厚的一件」，四条：
**软超时验尸 / 判官失败不打整单 / 空输出不作数 / 候选链降级**。

这四条都是产线上真炸过才补出来的。platform 若从零开始，等于把同样的坑再踩一遍，
而且是**在真实计费的前提下踩**。本期直接按同样语义实现（不复制代码——那是 studio 的
内部实现，跨产品直引已被契约测试禁止；照着行为重写一份）。

### 决定 3 · 一律在隔离 worktree 里执行

不给「直接在主工作区跑」这个选项。`worktree.prepare` 建独立工作树 → agent 在里面干活 →
`checkpoint` 提交 → `publish` 合并。主工作区全程零改动。

这也是下面决定 A 那个风险的**主要缓解手段**，所以它不是可选项。

## 三、必须仓主拍板的（三项）

### 拍板 A · 权限绕过开关 ⚠️ 最重要的一条

两个适配器组装出来的调用里，**默认都带着权限绕过**：

```js
// packages/providers/claude-cli.js
...(config.permissionArgs || ['--dangerously-skip-permissions']),
// packages/providers/codex-cli.js
...(config.permissionArgs || ['--dangerously-bypass-approvals-and-sandbox']),
```

适配器自己的注释解释了理由：

> 无头 `-p` 会话无法弹出权限确认；acceptEdits 只放行编辑，测试命令仍会反复被拒。
> 工单已运行在独立 worktree，且检查点会校验 write_scope，因此使用官方无头绕过开关。

**这个理由在 studio 的语境下成立**，但请注意它的实际含义：一个 AI agent 在你的机器上
**无人值守地执行任意命令**，唯一的边界是「它被放在一个 worktree 目录里」——那挡得住
误改主工作区，**挡不住** `rm -rf` 别处、读取本机凭据、发起网络请求。

三个选项：

| 选项 | 含义 | 代价 |
|---|---|---|
| **A1 照搬** | 沿用默认绕过 | 与 studio 一致，能跑通所有工单；风险如上 |
| **A2 收紧** | 配置 `permissionArgs` 为受限模式 | 部分需要跑命令的工单会卡住，得人工介入 |
| **A3 白名单** | 只对特定 role/项目放开绕过 | 实现复杂度上升，但风险面可控 |

**我的建议：A3。** 先只对 `reviewer`（只读角色，本来就不该写文件）用受限模式，
对 `backend`/`frontend` 用绕过但限定在 worktree 内。这样至少评审类工单不具备破坏力。

但这是你的机器、你的风险，**我不替你选**。

### 拍板 B · 花钱的闸门

`packages/budget` 至今**不存在**（总说明书列为「筹建」，`feat/budget-gate` 分支停在议题阶段）。
也就是说，本期没有现成的额度闸可用。

三个选项：

| 选项 | 含义 |
|---|---|
| **B1 先干等闸** | 执行链先跑通，额度闸等 `packages/budget` 落地再接 |
| **B2 本地薄闸** | platform 自己写一个最小额度闸（单次上限 / 日上限 / 总开关），不进 packages |
| **B3 先出 budget** | 先做 `packages/budget`（双签），再回来做执行链 |

**我的建议：B2。** 理由：B1 等于开着水龙头出门；B3 会把执行链无限期推后，而且
额度闸的真实需求要跑过才知道——先在 platform 本地攒经验，将来抽 packages 时更有依据。

薄闸的默认值我建议：**总开关默认关闭**，打开后单次上限与日上限都必须显式配置，
没配就拒绝执行（同工单库根目录那条：不猜、不兜底）。

### 拍板 C · 首次真实执行的方式

**建议：干跑（dry-run）默认开启。** 执行器默认只组装参数、走完全链路、写战绩，
但**不真的 spawn**——和现在的桩模式等价，只是链路全通。

要真跑必须显式 `{"干跑": false}`，且额度闸必须已配置。

这样第一次真花钱是一个**明确的、单次的、你亲手做的动作**，而不是「服务起来了就开始跑」。

## 五、验收标准

1. `npm run check` ✓、`npm test` ✓，新增 `test/执行链契约.test.js`；
2. **桩模式断言原封不动仍绿**——证明执行能力没进 `server.js` 闭包；
3. 干跑默认：不显式关闭时，全链路走完但零 spawn，可用进程树核验；
4. 额度闸未配置时拒绝真跑，且**报错路径上不产生任何调用**；
5. 反向验证：执行器未拉起时 `/api/execute/*` 优雅 503；越权工单号被拒；
6. 四条加固各有测试：软超时能验尸、空输出不记成功、判官失败不打整单、候选链能降级；
7. 战绩写入后 `/api/routing/rank` 的 `有区分度` 变为 `true`（端到端闭环）。

## 六、不做什么

- 不做并发调度（一次一单，跑通再说）；
- 不做质检/验收自动化（那是四态之外的事，见协-001 决定 1）；
- 不碰 studio、不碰 `packages/`；
- 不实现 `packages/budget`（若拍板 B2）。
