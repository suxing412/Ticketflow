# 议题 · platform 是一个产品，还是 studio 的第二套 profile？

> 2026-08-08 由 platform 迁入（刀一）过程中查出。**这是一个待你们两位拍板的问题，不是结论。**
> 我只负责把代码事实摆出来，并说明它为什么会连带决定「预算闸归属」那件事。

---

## 一、查出了什么

`apps/platform/README.md` 把 platform 描述为与 studio 并列的**另一个产品**：

> 本目录为 robinwang2 主导的通用软件开发协作平台预留（Orchestrator / 角色体系 /
> DAG 调度 / worktree 隔离 / 动态路由——设计完全自主）

但把原「通用多-Agent-协作平台重构」分支拆开看，代码事实不是这样。

那条分支相对 main 共 58 个文件变动：**29 个新增 + 29 个修改**。

**新增的是零件**（已按两刀重切落位）：

```
_app/lib/orchestration/plan.js          → apps/platform/lib/
_app/lib/routing/{router,history}.js    → apps/platform/lib/
_app/lib/workspace/worktree.js          → apps/platform/lib/
_app/lib/{toolchain,review-opinion}.js  → apps/platform/lib/
_app/lib/providers/*.js                 → packages/providers/
套件/角色协议模板/*.md（6 份）           → apps/platform/角色协议模板/
```

**修改的是 studio 的整机**：

```
_app/lib/core/{config,state,store}.js
_app/lib/{gates,pool,lifecycle,recommend,runner,staff,stages}.js
_app/main.js
```

`apps/platform/` 里**没有 server.js、没有 main.js、没有 public/**。

结论：**那条分支从来不是一个独立 app，它是被改造过的 studio。**
它借用 studio 的整机（HTTP 层、Electron 壳、执行器循环、目录即状态机），
只是插进 orchestration / routing / worktree / providers 几个模块，
再把「职能」体系换成「角色」（orchestrator / backend / frontend / reviewer / integrator）。

这不是批评那条分支——**作为改造它是成立的，而且被压过**：
它跑完了一个真实软件项目的 22 张单（求职平台 `海投王`，M0–M3 里程碑，
工作区 `AIStudioDev`，含 worktree 隔离与多角色评审）。问题只在于**它不是一台能单独开机的整机**。

## 二、于是有三条路

| | 做法 | 代价 |
|---|---|---|
| **A** | 给 platform 补整机（server / UI / executor） | 工作量最大，且两套 UI 各自维护、两套执行器各自演化 |
| **B** | **让 studio 支持 profile 切换**——`profile: software-project` 走角色 + providers 路由，`game` 走现在这套 | 那条重构分支本来就是这么干的，只是没做成开关；一套整机两套人格 |
| **C** | 维持现状，`apps/platform/` 长期是零件盒 | 疆界名存实亡，CODEOWNERS 那条线划着但没有东西在后面 |

## 三、为什么这件事必须先谈

因为**「预算闸归属」是它的下游**。

预算闸（施工令-021）现在落在 `apps/studio/lib/budget.js`。有人问：为什么不放 `packages/core`？
`packages/core/README.md` 自己把「双闸 / 额度纪律」列进了共享地基范围，
而 `budget.js` 零 studio 依赖（只 require `fs` / `path`）——按自述它确实是 core 的候选。

但答案取决于上面选哪条路：

- 选 **B**（一个整机两套 profile）→ 预算闸本来就在共用层，**归属问题自动消失**；
- 选 **A**（两个整机）→ 预算闸必须进 core，否则 platform 要复制一份；
- 选 **C** → 维持现状即可，没有第二个消费者。

所以建议的讨论顺序是：

> **① 一个整机还是两个 → ② core 抽哪些 → ③ 预算闸归属**

反过来先谈第 ③ 会卡住，因为它没有独立答案。

## 四、附赠：core 边界的实证答案

`packages/core/README.md` 说过它想要什么：

> 由 platform 的**实际消费方式**决定包的 API 形状，避免闭门造 API。

**那条重构分支改的那 12 个文件，就是这个问题的实测答案**——platform 为了跑起来必须动的模块，
就是共享地基的实际范围：

```
core/{config,state,store}  gates  pool  lifecycle  recommend  runner  stages
```

不用再猜了。抽 core 时按这份清单谈，比从概念出发准得多。

（顺带一提：`staff.js` 在这份清单里，但它已随 H85「去岗位化」在 studio 侧删除、
由 `roster.js` 取代。抽取时要确认 platform 侧的角色体系怎么落到 `roster` 的每职能一行模型上。）

## 五、我的倾向（仅供参考，不是主张）

倾向 **B**。理由是它同时解掉三个问题：
platform 不必重造整机；预算闸归属自动落地；两套 profile 共用一条经过实战加固的执行器
（软超时验尸、判官失败不打整单、空输出不作数、活尾巴取样——这些教训不该复制两份）。

代价是 studio 要接受「它不只是游戏工作室的驾驶舱」这个定位改变，
而这属于制作人裁量，不由我判。
