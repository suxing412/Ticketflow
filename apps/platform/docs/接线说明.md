> 复用 Ticketflow `packages/watchtower/接线说明.md` 的接法，本页只补**平台侧具体路径**。
> 瞭望塔正本住 `packages/watchtower`（单文件零依赖），本仓不复制正本，
> 由 `scripts/watchtower.js` 经 `lib/公用件` 从仓根 `packages/` 解析并代为拉起
> （`TICKETFLOW_PACKAGES` 可覆盖）。旧的「并排克隆 + `TICKETFLOW_HOME`」已随一仓合并作废。

## 一、装守护

```
npm run watchtower                 # 前台起守护（试跑/调试用，Ctrl+C 停）
npm run watchtower:install         # 注册登录自启计划任务（任务名 AI-DevPlatform瞭望塔）
schtasks /Run /TN AI-DevPlatform瞭望塔    # --install 只登记不当场启动，补这句拉起
```

任务名带平台前缀，避免与同机其他瞭望塔任务（如监制台侧的「瞭望塔」）撞名互踩；
卸载：`npm run watchtower -- --uninstall`（启动器会自动补同名 `--task-name`）。

验收三连：

- `npm run watchtower:status` → `在岗:true`，且心跳段 `在跳:true`（`watchtower-out/心跳.txt` 每 30s 覆盖写，断更即守护不在）；
- `npm run watchtower -- --toast-test` → 桌面弹出测试通知（BurntToast→气泡→msg 三档回落）；
- 看 `watchtower-out/瞭望塔流水.log` 有「瞭望塔上岗」行；
- 加一条平台侧的：开着 `npm start` 刷新 `http://127.0.0.1:4370`，在岗灯绿。

## 二、常驻会话挂监听（人不在，会话在）

开一个常驻 Claude Code 会话，把**统一流水**当唯一 tail 对象挂上 Monitor（或等价后台 tail）：

```
Monitor: tail D:\GitHub\AI-DevPlatform\watchtower-out\瞭望塔流水.log —— 出现「急」级行即唤起处置
```

- 一行一事件带信源标（`[流水] [信箱] [时钟] [心跳] [远端]`），急/常分级由 `config/规则.json` 定；
- 会话不在场的积压：回来先 `npm run watchtower -- --unread` 看账，处理完 `-- --ack all` 清账；
- 只挂这一个文件就够——五路信源全部收口到它。

# 四、lib/ 模块接线台账（2026-08-10）

在此之前，`lib/` 下六个模块**一个都没接到接口上**。它们写好了、测过了，但 `server.js`
全文只 require 了 4 个东西（`http`/`fs`/`path` + `lib/公用件`），没有任何代码路径走得到它们。
孤儿模块不会报错，只会安静地不存在——所以这份台账连同 `test/接线契约.test.js` 一起立着。

## 已接线（5/6）

判据只有一条：**不破坏桩模式的物理保证**（`server.js` 的依赖闭包里不得出现 `child_process`）。

| 模块 | 接口 | 性质 |
|---|---|---|
| `routing/router.js` | `GET /api/routing/rank?role=&kind=` | 纯计算，只排名不派发 |
| `routing/history.js` | `GET /api/routing/history?limit=&role=` | 只读 `journal/provider-runs.jsonl` |
| `toolchain.js` | `GET /api/toolchain` | 只查文件是否存在，不安装不下载 |
| `review-opinion.js` | `POST /api/review/parse` | 纯文本解析，无状态不落盘 |
| `orchestration/plan.js` | `POST /api/plan/validate` | 只解析校验，**不落盘**（落盘那半需注入工单库） |

## 未接线（1/6）——是决定，不是遗漏

**`workspace/worktree.js`** — 它 `require('child_process')`。接进 `server.js` 就等于让这台
服务能起真实进程，`server.js` 头部那句「任何路径都发不起真实 CLI 进程，零计费」当场失效。
这是出厂时刻意锁定的边界，要突破得是显式决定，不能顺手带进来。契约测试里有一条传递闭包
断言盯着，谁接谁红。

### 已解决：plan.js 的跨产品依赖

它原先 `require('../../../studio/lib/core/store')`，直接伸手进**另一个产品的内部模块**——
`docs/边界与协作.md` 定的规矩是公用件唯一家在仓根 `packages/`、双签共建，对方的内部实现
不是可依赖的 API（studio 改自己的内部结构时根本不会知道我们在用）。

**改法是把 store 变成注入**，而不是去动 studio：`materialize(root, cfg, parent, plan, store)`
由调用方把工单库递进来。于是纯计算的五个导出（`extractJson` / `configuredPlanFile` /
`resolvePlan` / `normalizePlan` / `bodyOf`）不再有任何跨产品依赖，当场可接线；落盘的
`materialize` / `consume` 等 platform 有了自有工单库再用，缺 store 时明确抛错，不静默降级
（悄悄什么都不写比直接失败难查得多）。

> 该盲区已补：`test/公用件契约.test.js` 新增一条断言，把相对 require 解析成真实路径后
> 判断是否跑出本产品目录且不在 `packages/` 下，跨产品直引即红。原先那条依赖面断言
> 认的是 `packages/xxx` 形态，`../../../studio/lib/...` 完全不在它雷达上。

## 排名的区分度：如实自曝，不假装有判断

`/api/routing/rank` 三家分数仍然全平。这不是缺陷，是**还没有可依据的数据**：
`providers.<名>.scores` 出厂留空（厂商孰优孰劣不该由出厂配置替仓主拍板），
`journal/provider-runs.jsonl` 也还没有战绩（桩模式不写账）。

处置不是编几个分数糊上去，而是让接口**自己说清楚**：响应新增 `有区分度` 字段，平局时
说明里写明「当前顺序仅按名称字母序，不代表评估结论」，并给出三条让排名产生信号的途径
（显式 `scores`、`routing.roles.<角色>.prefer` 偏好、或积累实际战绩）。

把「字母序第一」当成「评估最优」比没有排名更危险——它看起来像个判断，实际零信号。

`config/platform.config.json` 同批补了两段：
- `roles` — 角色词表。不是随手起的，是 `plan.js` 的既有契约（它按 roles 的键校验子任务
  角色，并对 reviewer 设了只读约束）。缺这段时任何计划都判「使用未知角色」。
- `routing.weights` — 加权策略。数值与 `router.js` 的内置默认一致，**填上不改变当前行为**，
  只是把隐式默认变成显式声明，让公式可见可调。
