## 一、装守护

```
npm run watchtower                 # 前台起守护（试跑/调试用，Ctrl+C 停）
npm run watchtower:install         # 注册登录自启计划任务（任务名 AI-DevPlatform瞭望塔）
schtasks /Run /TN AI-DevPlatform瞭望塔    # --install 只登记不当场启动，补这句拉起
```

任务名带平台前缀，避免与同机其他瞭望塔任务（如监制台侧的「瞭望塔」）撞名互踩；
卸载：`npm run watchtower -- --uninstall`（启动器会自动补同名 `--task-name`）。

验收三连：

- `npm run watchtower:status` → `在岗:true`，且心跳段 `在跳:true`（`watchtower-out/心跳.txt` 每 30s 覆盖写，断更即守护不在）；
- `npm run watchtower -- --toast-test` → 桌面弹出测试通知（BurntToast→气泡→msg 三档回落）；
- 看 `watchtower-out/瞭望塔流水.log` 有「瞭望塔上岗」行；
- 加一条平台侧的：开着 `npm start` 刷新 `http://127.0.0.1:4370`，在岗灯绿。

## 二、常驻会话挂监听（人不在，会话在）

开一个常驻 Claude Code 会话，把**统一流水**当唯一 tail 对象挂上 Monitor（或等价后台 tail）：

```
Monitor: tail D:\GitHub\AI-DevPlatform\watchtower-out\瞭望塔流水.log —— 出现「急」级行即唤起处置
```

- 一行一事件带信源标（`[流水] [信箱] [时钟] [心跳] [远端]`），急/常分级由 `config/规则.json` 定；
- 会话不在场的积压：回来先 `npm run watchtower -- --unread` 看账，处理完 `-- --ack all` 清账；
- 只挂这一个文件就够——五路信源全部收口到它。

# 四、lib/ 模块接线台账（2026-08-10）

在此之前，`lib/` 下六个模块**一个都没接到接口上**。它们写好了、测过了，但 `server.js`
全文只 require 了 4 个东西（`http`/`fs`/`path` + `lib/公用件`），没有任何代码路径走得到它们。
孤儿模块不会报错，只会安静地不存在——所以这份台账连同 `test/接线契约.test.js` 一起立着。

## 已接线（5/6）

判据只有一条：**不破坏桩模式的物理保证**（`server.js` 的依赖闭包里不得出现 `child_process`）。

| 模块 | 接口 | 性质 |
|---|---|---|
| `routing/router.js` | `GET /api/routing/rank?role=&kind=` | 纯计算，只排名不派发 |
| `routing/history.js` | `GET /api/routing/history?limit=&role=` | 只读 `journal/provider-runs.jsonl` |
| `toolchain.js` | `GET /api/toolchain` | 只查文件是否存在，不安装不下载 |
| `review-opinion.js` | `POST /api/review/parse` | 纯文本解析，无状态不落盘 |
| `orchestration/plan.js` | `POST /api/plan/validate` | 只解析校验，**不落盘**（落盘那半需注入工单库） |

## 未接线（1/6）——是决定，不是遗漏

**`workspace/worktree.js`** — 它 `require('child_process')`。接进 `server.js` 就等于让这台
服务能起真实进程，`server.js` 头部那句「任何路径都发不起真实 CLI 进程，零计费」当场失效。
这是出厂时刻意锁定的边界，要突破得是显式决定，不能顺手带进来。契约测试里有一条传递闭包
断言盯着，谁接谁红。

### 已解决：plan.js 的跨产品依赖

它原先 `require('../../../studio/lib/core/store')`，直接伸手进**另一个产品的内部模块**——
`docs/边界与协作.md` 定的规矩是公用件唯一家在仓根 `packages/`、双签共建，对方的内部实现
不是可依赖的 API（studio 改自己的内部结构时根本不会知道我们在用）。

**改法是把 store 变成注入**，而不是去动 studio：`materialize(root, cfg, parent, plan, store)`
由调用方把工单库递进来。于是纯计算的五个导出（`extractJson` / `configuredPlanFile` /
`resolvePlan` / `normalizePlan` / `bodyOf`）不再有任何跨产品依赖，当场可接线；落盘的
`materialize` / `consume` 等 platform 有了自有工单库再用，缺 store 时明确抛错，不静默降级
（悄悄什么都不写比直接失败难查得多）。

> 该盲区已补：`test/公用件契约.test.js` 新增一条断言，把相对 require 解析成真实路径后
> 判断是否跑出本产品目录且不在 `packages/` 下，跨产品直引即红。原先那条依赖面断言
> 认的是 `packages/xxx` 形态，`../../../studio/lib/...` 完全不在它雷达上。

## 排名的区分度：如实自曝，不假装有判断

`/api/routing/rank` 三家分数仍然全平。这不是缺陷，是**还没有可依据的数据**：
`providers.<名>.scores` 出厂留空（厂商孰优孰劣不该由出厂配置替仓主拍板），
`journal/provider-runs.jsonl` 也还没有战绩（桩模式不写账）。

处置不是编几个分数糊上去，而是让接口**自己说清楚**：响应新增 `有区分度` 字段，平局时
说明里写明「当前顺序仅按名称字母序，不代表评估结论」，并给出三条让排名产生信号的途径
（显式 `scores`、`routing.roles.<角色>.prefer` 偏好、或积累实际战绩）。

把「字母序第一」当成「评估最优」比没有排名更危险——它看起来像个判断，实际零信号。

`config/platform.config.json` 同批补了两段：
- `roles` — 角色词表。不是随手起的，是 `plan.js` 的既有契约（它按 roles 的键校验子任务
  角色，并对 reviewer 设了只读约束）。缺这段时任何计划都判「使用未知角色」。
- `routing.weights` — 加权策略。数值与 `router.js` 的内置默认一致，**填上不改变当前行为**，
  只是把隐式默认变成显式声明，让公式可见可调。

# 五、门禁（2026-08-10）

## 挡的是什么

`server.js` 绑 `127.0.0.1`，挡得住局域网里的别的机器，**挡不住你自己浏览器里的页面**——
浏览器就在 localhost 上。而 `收体()` 不看 `Content-Type`，拿到什么都直接 `JSON.parse`。

两件事凑一起就有条路：用 `Content-Type: text/plain` 发 JSON 属于跨域**简单请求**，
不触发 CORS 预检，于是你随手打开的任何网页都能往 `127.0.0.1:4370` 发 POST 并被执行到底。
浏览器只拦住它*读取*响应，请求本身照发不误——对会改状态的接口来说，伤害已经造成。

这条路是实测确认的，不是推演：伪造 `Origin: https://evil.example` + `text/plain`，
接口照收，返回 `"ok": true`。

补门禁之前它不构成风险，因为三个 POST 全是纯的（echo 是桩、review/parse 与 plan/validate
只算不写），最坏结果是白算一次。但这正是接 `workspace/worktree.js` 之前必须先补的东西——
那个模块会 `git commit` / `git merge`。

## 三道闸

按从便宜到贵排：

| 闸 | 规则 | 挡谁 |
|---|---|---|
| ① Origin | 带 `Origin` 且非本站来源 → **403** | 浏览器里的跨站页面 |
| ② Content-Type | POST 非 `application/json` → **415** | 「简单请求」免预检那条路 |
| ③ 令牌 | 缺/错 `Authorization: Bearer` → **401** | 本机其它进程 |

`curl` 与瞭望塔守护不带 `Origin`，前两道对它们天然放行——它们本来也不在威胁模型里。

## 三件配套决定

**门禁在路由之前。** 放在之后的话，未知路径的 404 会泄露「哪些接口存在」。未授权者不该
有能力区分「这条不存在」和「这条存在但你进不来」，所以未授权时一律 401。

**`/api/health` 免令牌，且只此一条。** 瞭望塔守护按 `config/瞭望塔.config.json` 的心跳
地址探它，而守护住在仓根 `packages/`（双签共建），我们没法单方面让它带令牌。它只吐
版本/端口/路径，跨域又读不到响应，例外成本可接受——Origin 与 Content-Type 两道闸对它
照样生效。契约测试钉死了这份名单，加条目必须是显式决定。

**令牌随首页注入，UI 一行不改。** 服务发 `index.html` 时在 `</head>` 前插一段脚本，
包住 `window.fetch` 给同源 `/api/` 请求自动补上 `Authorization` 与 JSON 头。
跨站页面读不到本页内容，也就拿不到令牌。

## 用法

令牌落在 `config/接口令牌.local.json`（被 `.gitignore` 的 `*.local.json` 挡住，不入库），
开机日志会打印路径。浏览器打开首页无需手工填；`curl` 需要自己带：

```
curl -H "Authorization: Bearer $(node -p "require('./config/接口令牌.local.json').令牌")" \
     http://127.0.0.1:4370/api/providers
```

令牌落盘复用不每次重生成，否则存下来的 curl 别名每次重启都失效。**要轮换就删掉那个文件
再起服务。**

## 还没做的（接 worktree 前的剩余三步）

门禁只是第 1 步。`workspace/worktree.js` 仍未接，后面还有：

2. 只读的先接（`worktree list` / `diff` / `changedFiles`），风险与现在无异；
3. 写操作（`worktree add` / `add -A` / `commit` / `merge`）单独隔离，不进 `server.js`
   的依赖闭包，让那条传递闭包断言继续守着 server 本身；
4. 改断言而不是删断言——把「禁止 child_process」调整成明确的例外清单，
   让下一次误接仍然会红。

# 六、工作区隔离（2026-08-10）—— 接 worktree 四步的第 2/3/4 步

## 先纠正一处判断

第五节末尾我把剩余步骤写成「只读的先接，风险与现在无异」。**那句不准确。**

`worktree.js` 里所谓的只读函数——`isGitRepo` / `repoTop` / `worktreeList` / `changedFiles`——
底下全是 `spawnSync('git', ...)`。读 git 状态**照样要起进程**。所以「只挑只读的接」并不能
绕开「server.js 任何路径都发不起真实进程」这条保证，它只是不改仓库而已。

结论：绕不过去，只能隔离。

## 方案：把 git 能力挪出 server 的进程

```
浏览器 / curl
     │  /api/workspace/*      （带令牌）
     ▼
server.js ──── http 转发 ────► scripts/工作区服务.js ──► git 子进程
（只用 http，                  （唯一持有 worktree.js
  永不 spawn）                   的地方，独立端口 4371）
```

`server.js` 的依赖闭包依旧零 `child_process`，所以**那条传递闭包断言一个字都没改**。

这就是第 4 步的答案：不是「把禁止改成例外清单」，而是**根本不需要例外**。
实测确认：故意把 `worktree.js` 直接 require 进 `server.js`，原断言当场点名
「lib\workspace\worktree.js 引入了 child_process」。

## 接口

隔离进程自己也有门禁（同一个令牌文件），**没有免令牌例外**——瞭望塔不探它，
没有非带不可的理由。

| 经 server 的路径 | 作用 |
|---|---|
| `GET /api/workspace/health` | 服务自述：仓根、写开关状态 |
| `GET /api/workspace/repo?dir=` | 是否 git 仓、仓顶在哪 |
| `GET /api/workspace/worktrees?repository=` | worktree 清单 |
| `GET /api/workspace/changes?dir=` | 已改动文件清单 |
| `*/write/*` | 写操作，默认 **403 未启用** |

路径一律用 ASCII。中文路径踩过坑：`new URL().pathname` **不解码**百分号编码，
而浏览器与 curl 都会编码，于是 `路径 === '/仓库信息'` 对任何规范客户端都匹配不上。

## 三道防线

**路径闸。** 传进来的 `dir` / `repository` 一律收窄到仓根之内，越界即 400。
不做这关的话，带令牌的调用方可以拿 `dir=C:\` 把本机的 git 仓库探个遍。
实测：`dir=../../../Windows` → `路径越界：只允许仓根 D:\Ticketflow 之内`。

**写开关。** `config/platform.config.json` 的 `workspace.允许写`，默认 `false`。
把 `git commit` / `merge` 挂到 HTTP 上是一项**独立的授权决定**，不该由「服务起来了」
顺带获得。开启后也只回 501 未实现——具体哪个写操作要暴露、以什么形状暴露，逐个决定逐个做。

**优雅降级。** 隔离进程默认不随 server 启动。没拉起来时转发返回 503 并说明
`npm run workspace`，而不是把 500 甩给调用方。

## 用法

```
npm run workspace     # 拉起隔离进程（默认 4371），要用工作区接口才需要
npm start             # 平台服务照常，不依赖上面那个
```

两个进程互不阻塞：工作区服务没起，平台其余接口一切照常。
