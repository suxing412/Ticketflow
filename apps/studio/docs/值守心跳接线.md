# 值守心跳接线说明（TK-210 / TF-4）

> 本文是**会话侧接线的唯一可查依据**，也是 `lib/pm/watchpulse.js` 里 `应有项数` 这个常数的**校对源**。
> 在此之前接线只散在两个源码头注里（`server.js` 的节拍器 hunk、`scripts/值守在位.js` 的文件头），
> 仓内没有一份能拿来对账的文档，而值守清单本体住在仓外（`~/.claude/skills/watch-rearm`）——
> 清单增减时 `应有项数` 无从校对。本文补的就是这一段。

## 0. 这条脉冲治的是什么病

值守六项全挂在会话内 `Monitor(persistent)` 与 cron 上，两者都随进程重启而灭。
watch-rearm 附则给的验活法「近 10 分钟内应有事件是否收到通知」**在安静时段不成立**：
没有真实事件时，「没事发生」与「监视器已死」长得一模一样。

于是监制台**自造一条稳定脉冲**：每 5 分钟往当月 journal 追加一行带单调 seq 的心跳。
值守会话订阅它、每被唤醒一次跑一遍 watch-rearm、然后回执。连续 3 拍收不到回执 = 塔死了 → 急件 + G25。

两侧只认 `lib/pm/watchpulse.js` 导出的常量与行格式函数，**周期/阈值/报文各只有一把尺**。

## 1. 会话侧 Monitor 的订阅关键词与 persistent 语义

| 项 | 值 | 出处 |
|---|---|---|
| 订阅关键词 | `值守心跳` | `watchpulse.心跳关键词` |
| 数据源 | 监制台当月 journal（心跳行由 `journal.append` 落进去） |
| persistent | **必须 `persistent: true`** | watch-rearm 附则（2026-08-11 两次漏报案） |

心跳行的样子（由 `watchpulse.心跳行()` 独家拼装，谁都不许就地拼字符串）：

```
值守心跳 seq=42 应有=7 周期=5m
值守心跳 seq=43 应有=7 周期=5m restart=1
```

- 关键词就是**行首标记**，过滤词与行首标记是同一个串——不是两处各写一个。
- `restart=1` 只标**本进程首拍**。看见它就等于监制台刚重启过：会话侧应当**立刻跑一轮完整重挂**，
  因为进程重启这件事历史上四犯（08-06 13:40 三振急件漏看 45 分钟；08-06 15:03 只重挂信箱线、
  流水线裸奔 90 分钟；08-11 两次后台 tail 有货不唤醒）。
- `seq` **跨重启只增不减**（水位落在 `.值守心跳.json`，不在内存）。会话侧读到的 seq 就是回执要写回去的那个数。
- 禁用后台 Bash `tail` 方式订阅——缓冲有货但不唤醒，这正是 08-11 两次漏报案的形态。

## 2. 每次唤醒要跑的 watch-rearm 动作序列

被心跳唤醒一次 = 跑一遍下面三步，一步都不许省：

1. **List 比对**：`CronList` + `TaskList` 各跑一次，与第 4 节的清单**逐项**比对。
   不许凭印象说「应该还在」——「进程还在 ≠ 监视还在」是本条的全部案由。
2. **补挂**：缺哪项挂哪项。月初注意第 1 项的日志文件名换月。
3. **再 List 确认在册**：补完再 `CronList` + `TaskList` 一次，确认新挂的**真的在册**。
   `已挂` 报的是这一步**实测在册**的项数，不是「应该有几项」（那是 `应有项数`）。

跑完调第 3 节的 CLI 回执。**有补挂才向窗口报一行，无补挂静默**——不刷屏是这条协议的一半价值。

## 3. 回执 CLI：`scripts/值守在位.js`

```
node scripts/值守在位.js --seq <N> --已挂 <M>
node scripts/值守在位.js --seq <N> --已挂 <M> --补挂 流水关键事件监视,信箱急件监视
```

| 参数 | 含义 | 备注 |
|---|---|---|
| `--seq N` | 本次处理的心跳序号（从心跳行里读出来的那个数） | 必填；非正整数一律拒收 |
| `--已挂 M` | 第 2 节第 3 步**实测在册**的项数 | 缺省记 `?` |
| `--补挂 a,b` | 本次补挂了哪几项，逗号（`,` `，` `、` 均可）分隔 | 省略或空 = 无变更 |
| `--root <路径>` | 数据根 | 缺省走 `core/config.resolveRoot()`，与 server 同一把尺 |

- `--k v` 与 `--k=v` 两式都收。
- **退出码**：`0` 成功；`1` 参数非法或写盘失败。会话侧据此判「回执没写上」，
  **不许当成写上了**——假在位会把三振对账整个骗过去。
  特别地：`--seq` 后面漏了值会被解析成布尔 `true`，CLI 显式挡掉并以 `1` 退出（`Number(true) === 1`，
  不挡就会把一次写错的调用静默记成「seq 1 已在位」）。
- **有变更时** stdout 打一行窗口报文，原样贴进窗口：

  ```
  瞭望塔第 3 次静默阵亡，已自动重挂 7/7（缺 流水关键事件监视 已补）
  ```

  无变更时**一个字都不打**。
- 回执**只许前进**：迟到的旧 seq 不会把水位拽回去（拽回去就会凭空造出一次假阵亡）。
- 走 node CLI 而不是 HTTP：回执写的是盘上 state 文件，server 正在换装时回执照样落盘；
  且中文项名不进 curl 的 argv（本仓根治过的编码坑）。

## 4. 值守清单 7 项（逐项点名）

**`应有项数 = 7` 以本节为校对源**：本节增减一项，`lib/pm/watchpulse.js` 的 `应有项数` 必须同步改，
`test/watchpulse.test.js` 的协议常量那一格会当场红。

第 1–6 项誊自 `~/.claude/skills/watch-rearm` 的《值守清单（正本）》，第 7 项是本单新增。

| # | 器材 | 规格要点 | 在册判据 |
|---|---|---|---|
| 1 | 流水关键事件监视 | `tail -n 0 -f <监制台>/journal/<当月>.log`，过滤 `完成｜执行失败｜待重派｜上呈｜三振｜收口｜专项｜初检不过｜核查不过｜停滞｜告警`（grep 必须 `--line-buffered`） | `TaskList` 见 persistent monitor |
| 2 | 信箱急件监视 | `tail -n 0 -f <监制台>/呼叫/inbox.jsonl` | `TaskList` 见 persistent monitor |
| 3 | cron 晨报 | 主拍 09:03 每日 → `morning-report`；**备份拍 09:12**（主拍已出报即静默） | `CronList` 命中**两条**（主拍+备份拍） |
| 4 | cron 晚报 | 23:26 每日 → `evening-report` | `CronList` 命中 |
| 5 | cron 切夜班 | 00:00 每日 → `night-shift` | `CronList` 命中 |
| 6 | 在飞任务监视 | 按当下在飞事项补挂（测试落地 watcher、换装静默窗等），临时性，完成自灭 | 逐事项判断 |
| 7 | **值守瞭望塔自身**（本单新增） | 只订阅 `值守心跳` 的 `Monitor(persistent)`，被唤醒即跑第 2 节序列并按第 3 节回执 | `TaskList` 见该 persistent monitor；监制台侧另有 G25 兜底 |

> 第 7 项是「看守者的看守者」：前六项由它自动重挂，它自己静默阵亡时整条链退回单点，
> 而那一刻最不可能有人喊——故它的在册与否由**监制台侧**（不是会话侧）判定，落在 G25 上。
>
> **名词警戒**：本仓 `瞭望塔` 一词已被 `packages/watchtower` 那只常驻守护占着（30s 覆盖写 `瞭望塔/心跳.txt`，
> G14/G20 键在它身上）。本文说的一律是**值守会话侧第 7 项监视**，与那只守护毫无关系；
> 闸名带「值守」前缀就是为了让 journal 行与闸不歧义。

## 5. 三个数：本文档值 vs 代码常量

| 数 | 本文档 | `lib/pm/watchpulse.js` | 对得上 |
|---|---|---|---|
| 心跳周期 | 5 分钟 | `周期毫秒 = 5 * 60000`（＝300000ms＝5 分钟） | ✓ |
| 三振阈值 | 连续 3 拍无回执判亡 | `三振阈值 = 3` | ✓ |
| 应有项数 | 第 4 节 7 项（六项 + 瞭望塔自身） | `应有项数 = 7` | ✓ |

顺带（同为协议面，不在工单点名的三数之列）：订阅关键词 `值守心跳` ＝ `心跳关键词`；
state 文件 `.值守心跳.json` ＝ `STATE_FILE`。

## 6. 监制台侧：判亡与销债

- 节拍器挂在 `server.js` 既有定时器族里（`setInterval(...).unref()`），**不另起常驻进程**；
  `initError` 或 `STUB` 桩台一律不拍。
- 对账只算 **seq 之前**的拍：缺失区间 `[在位.seq+1, seq-1]`。首拍区间为空，天然不判亡。
- 连续 `三振阈值` 拍无回执 → **进入阵亡态的那一次跃迁**上发急件（`级=急`，`类型=值守塔阵亡`）+ journal 留痕：

  ```
  值守瞭望塔静默阵亡：连续 3 拍无在位回执（缺失 seq 2~4）
  ```

  告警挂在跃迁上、不挂在「无回执 ≥ 阈值」这个持续为真的条件上——后者每拍复喊一封，
  把急件变噪声（inbox 377 条未读案）。
- 收到回执即复位（journal 留一行「已恢复在位」），**复位后再死照喊第二封**，不是喊过一次就永久闭嘴。
- 看板消费端是 **G25**（归总监，响应型，落点「总览 · 值守」，按钮「重挂瞭望塔」）。
  它**只读**监制台侧那份对账结论（`.值守心跳.json` 的 `阵亡` 位），不在消费端第二次算阈值——
  两处各写一个数就是两把尺（G16 判例）。塔恢复在位后当场销债（G14 恒真闸的教训）。

## 7. 运行态落盘
